## Findings

### M8 — unexpected survivor (now remediated)

**What happened:** M8 removed the `version = version + 1` increment from
`recordRun`'s UPDATE statement. The suite still passed because the only check
exercising `version` was `stale write rejected by version check`, which uses
`updatePayload` — and `updatePayload` still incremented version correctly.
`recordRun`'s version column was never directly asserted.

**Why it matters:** the concurrency gate (`concurrency.mjs`) verifies
`version = WRITERS` after 16 writers each UPSERT the same row. That check is
Postgres-only and currently INCONCLUSIVE. The SQLite invariant suite was the
only coverage of `recordRun`'s version semantics, and it had a gap.

**Remediation:** added `recordRun increments version on each update` to the
invariant suite. Three consecutive `recordRun` calls on the same signature must
produce `version = 3`. M8 re-run after patch: `FAIL recordRun increments
version on each update — version=1`. Gap closed.

**New suite count:** 26 checks (was 24 before this run; 25 after gap closure;
26 after inv.ts was re-counted — the original summary of "24" undercounted
the repo section which had 13 checks, not 11).

### M11 — killed by wrong instrument

**What happened:** the named expected kill was `exactly one row for a repeated
signature` (a soft assertion). The actual kill was the SQLite PRIMARY KEY
constraint raising `UNIQUE constraint failed` — a hard crash before the
assertion was reached.

**Why it matters:** the crash is a valid and stronger form of detection. But
the invariant that was supposed to catch it did not fire. This is not a gap —
the constraint is the correct primary defence — but it means the named check
has never been tested in a scenario where the constraint is absent (e.g.
Postgres with a different conflict resolution path). Noted, not actioned.

### M13 — killed by adjacent check

**Predicted kill:** `tenant A never observes tenant B values`
**Actual kill:** `identical signature in two tenants stays two rows`

SQLite returned org_A's row for both tenant queries, so `aRow.slackPs` was -90
(not 999), and the "never observes" check passed vacuously. The adjacent check
caught it because the payload comparison across tenants failed.

**Implication:** the tenant isolation test would be stronger if the cross-tenant
query was explicitly forced to prefer the other tenant's row (e.g. by inserting
org_B first, or by checking that both org_A and org_B have correct payloads in
separate assertions). The current structure is fragile to SQLite row ordering.
This is a coverage note, not a correctness defect.

## Predicted survivors requiring new fixtures

### M7 — NFC normalisation gap

**Fixture needed:** a hierarchy name containing a combining character sequence,
e.g. `u_café` (U+0061 U+0301, decomposed `á`) vs `u_café`
(precomposed NFC). Both must canonicalise to the same hierarchy name and produce
the same signature.

**Context:** real designs from non-ASCII EDA toolchains (Japanese, Korean, or
tool-generated names with accent marks) would expose this immediately. Synthetic
English-only fixtures cannot.

### M15 — sort-order gap

**Fixture needed:** a semantic key where field-name sort and value sort diverge.
Example: fields `['mode', 'corner']` sort alphabetically as `corner < mode`,
but if the values were `['func', 'abc']`, value-sort gives `abc < func` →
same order, no divergence. A diverging example: field `z_field` with value
`aaa` paired with field `a_field` with value `zzz`. Field sort: `a_field` first.
Value sort: `aaa` first (same result here). Need fields where value-alphabetical
order differs from field-alphabetical order.

Concrete fixture: `[['z_endpoint', 'aardvark'], ['a_startpoint', 'zebra']]`.
Field sort: `a_startpoint=zebra` + `z_endpoint=aardvark`.
Value sort: `z_endpoint=aardvark` + `a_startpoint=zebra`.
These produce different canonical strings → M15 would be killed.
