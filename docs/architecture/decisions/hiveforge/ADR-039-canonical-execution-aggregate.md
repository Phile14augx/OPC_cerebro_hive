# ADR-039: Canonical Execution aggregate

**Status:** Proposed (Phase 9a of `09-EXECUTION-LIFECYCLE-RUNTIME.md`; closes that phase's own placeholder — "tentatively 'the Execution Lifecycle ADR' — number not yet assigned" — now assigned)

## Context

`audit/SLICE-5-EXECUTION-LIFECYCLE-REVIEW.md` found six independent, non-communicating representations of "an execution" in this repository: `packages/database`'s `WorkflowExecution`/`AgentExecution` (plain, unconstrained `status` strings; the one live, actively-written schema), `packages/db`'s differently-shaped equivalents with a real, well-designed `ExecutionStatus` enum (`QUEUED`/`RUNNING`/`WAITING_FOR_HUMAN`/`COMPLETED`/`FAILED`/`TIMEOUT`/`CANCELLED`) but stranded in an unwired tree (`audit/SERVICES-PLATFORM-API-CLASSIFICATION.md` recommended archival, not adoption), `packages/domain`'s `AgentExecutionContext` (uses `traceId` as an execution-identity substitute, which the review found identifies nothing once persisted), `services/swarm-runtime`'s mocked `TaskDAG`, and `apps/platform`'s client-only Studio simulator. None share an ID space or a status vocabulary. `09-EXECUTION-LIFECYCLE-RUNTIME.md` formalized closing this as Phase 9, with a governing invariant that exactly one canonical `Execution` aggregate must be the only authoritative execution identity in the platform, and named 9a — this ADR's subject — as the first sequenced sub-phase, a prerequisite for 9b–9f.

This ADR is scoped to what 9a's own scope note commits to deciding: the aggregate's identity, status vocabulary, and structural shape. It is explicitly **not** scoped to transition legality (9b), persistence implementation (9d), event publishing (9e), or policy/cancellation enforcement (9f) — each of those remains open, per `09-EXECUTION-LIFECYCLE-RUNTIME.md`'s own non-goals section, and is not decided by this document.

## Decision

**1. `packages/domain`'s new `Execution` aggregate (`packages/domain/src/execution/`) is the one canonical execution identity.** Every execution-producing subsystem — agent, workflow, tool invocation, evaluation run, scheduler, or anything built later — is expected to construct and reference this aggregate's `ExecutionId`, not a subsystem-specific identifier. This directly supersedes `AgentExecutionContext`'s `traceId`-as-execution-id substitute as the platform's execution identity; `traceId` remains a real, separate field on `Execution` (distributed tracing), it is simply no longer doing double duty as an identifier.

**2. `ExecutionStatus` is a single, unified ten-value vocabulary, deliberately built as a superset of `packages/db`'s stranded-but-well-designed enum.** `CREATED`, `VALIDATING`, `QUEUED`, `RUNNING`, `WAITING`, `CANCELLING`, `COMPLETED`, `FAILED`, `CANCELLED`, `TIMED_OUT`. This reuses `packages/db`'s real design work (`QUEUED`/`RUNNING`/`WAITING_FOR_HUMAN`→`WAITING`/`COMPLETED`/`FAILED`/`TIMEOUT`→`TIMED_OUT`/`CANCELLED`) rather than re-inventing it from a clean slate, per this masterplan's own "inventory before contracts" discipline, and adds `CREATED`/`VALIDATING`/`CANCELLING` to cover states the 9b lifecycle diagram requires that `packages/db`'s enum didn't need to represent. `packages/database`'s plain, unconstrained `status` strings are not adopted as the vocabulary — they are the thing this vocabulary replaces.

**3. This vocabulary fixes valid values only, not valid transitions.** `Execution.recordStatus()` performs no transition-legality check by design, and documents that fact in its own comment. Which transitions are legal, and whether illegal ones are rejected, is 9b's decision, layered on top of this aggregate — this ADR does not pre-empt it.

**4. The aggregate distinguishes strict parent/child hierarchy from looser contributor cross-references.** `childExecutionIds` models strict ownership (e.g., a Workflow execution's own step executions); `contributorExecutionIds` models a non-owning cross-reference (e.g., an Evaluation execution referencing the Agent execution it evaluated). These are deliberately separate fields, not one overloaded relationship, because the review found real cases (an evaluator referencing an already-completed execution it doesn't own) that a single hierarchy field cannot represent without conflating "who spawned this" with "what does this relate to."

**5. `ExecutionId` is a plain value object in `packages/domain`'s own existing style, not a `packages/domain-model` branded `Identifier<Brand>`.** `packages/domain` and `packages/domain-model` are different bounded contexts with no dependency between them today (`packages/domain-model/README.md`'s own non-goals). Introducing that cross-package dependency for one type is a larger architectural decision than this aggregate needs to force; if it is made later, it is this ADR being amended, not a silent default.

**6. Neither `packages/database`'s nor `packages/db`'s existing schema is adopted wholesale as the persistence model.** `packages/db`'s enum is reused at the vocabulary level (decision 2) but its tree remains classified as a design reference per `audit/SERVICES-PLATFORM-API-CLASSIFICATION.md`, not resurrected. `packages/database`'s schema remains the live, actively-written one and is not replaced by this ADR — migrating it (adding an `ExecutionId`-shaped column, constraining `status` to this vocabulary, or wrapping it with an adapter) is explicitly deferred to Phase 9d, which owns persistence. This ADR fixes identity and vocabulary; it does not fix a migration plan or a schema.

**7. `ExecutionRepository` is a contract only.** The interface (`save`/`findById`/`findChildren`) is fixed by this sub-phase so 9c/9d have a stable shape to build against, but no implementation exists yet, and none is created by this ADR. It uses `packages/domain`'s own opaque `ITransactionContext`, not `@cerebro/database`'s Prisma-coupled `IRepositoryOptions`, for the same bounded-context reason as decision 5.

## Consequences

- This ADR does not change any live behavior. `conversations.routes.ts`, `AgentRuntimeService`, and `workflows.routes.ts` do not yet construct or persist an `Execution` — adopting this aggregate at those call sites is unresolved future work (likely 9c's orchestrator, or an explicit earlier migration step), not implied as complete by this decision or by `09-EXECUTION-LIFECYCLE-RUNTIME.md`'s own 9a exit criterion, which remains unmet until that adoption happens.
- `packages/database`'s and `packages/db`'s schemas are unaffected on disk. No migration has been written. A future reader must not infer "canonical aggregate exists" as "database schema updated" — those are separate facts, and only the former is true as of this ADR.
- `ExecutionEvents.ts`'s ten event-shape classes (`ExecutionCreatedEvent` through `ExecutionTimedOutEvent`) extend `packages/domain`'s own real, already-implemented `DomainEvent` base class, not HiveForge's `HiveDomainEvent` (`packages/domain-model`, Slice 3, zero implementations or consumers) — reuse of a working implementation over an unused contract, consistent with `09-EXECUTION-LIFECYCLE-RUNTIME.md` §9e's own framing of that same choice, though 9e's own scope note reserves the final say on which event system becomes canonical platform-wide. No event is published anywhere by this ADR — that is 9e's job.
- `ADR-022` (Resource Lifecycle State Machine) solved a structurally similar problem for infrastructure Resources, a different bounded context. This ADR does not reuse `ADR-022`'s transition-legality mechanism (out of scope, per decision 3) but its precedent is worth reading again once 9b is drafted.

## Implementation status — Complete for 9a's own scope (identity, vocabulary, aggregate shape, repository contract, event shapes); not yet adopted anywhere live

`packages/domain/src/execution/{ExecutionId.ts, ExecutionStatus.ts, Execution.ts, ExecutionRepository.ts, ExecutionEvents.ts}` exist and are exported from `packages/domain`'s root `index.ts`. Verified, not assumed:

- Real `tsc --strict` typecheck (via this repository's established scratch-toolchain pattern, since the workspace's own `pnpm`/`tsc` binaries are non-functional) against all five new files and their tests — clean, zero errors. One real bug was caught and fixed during this verification: `Execution.recordStatus()` initially attempted to mutate `startedAt`/`completedAt` on a `readonly`-typed props object; fixed by constructing the next immutable snapshot instead of mutating in place.
- Real `vitest` run — 28/28 tests passing, covering: `ExecutionId` generation/uniqueness/round-tripping/empty-value rejection; `Execution.create()`'s structural invariants (non-empty `kind`/`tenantId`/`traceId`/`correlationId`, no self-parenting, non-terminal initial status); `recordStatus()`'s `startedAt`/`completedAt` timestamp behavior and its deliberate non-enforcement of transition legality; idempotent `addChildExecution`/`addContributorExecutionReference` and their independence from each other; metadata defaulting and preservation; and all ten `ExecutionEvents` classes' payload shapes.
- Scratch verification artifacts (temporary `node_modules` symlinks, scratch `tsconfig`/`vitest.config`) were removed after the run — nothing left behind in `packages/domain/node_modules` beyond what was already there.
- Not yet done, and not claimed as done: any call site adopting `Execution`/`ExecutionId` in place of its current representation; any `ExecutionRepository` implementation; any event publication; any transition-legality enforcement. Each belongs to a later sub-phase named above.
