# ADR-045: Execution Reliability & Ownership — Retry, Idempotency, Leases, Failure Classification (Phase 9f-2)

**Status:** Proposed (Phase 9f-2 of `09-EXECUTION-LIFECYCLE-RUNTIME.md`; builds on `ADR-039` through `ADR-044`)

## Context

`ADR-044` (Phase 9f-1) covered "can this Execution legally move from state A to state B, and who is allowed to make it?" — authorization, cancellation, timeout. The second half of 9f's original scope, split off per explicit direction, answers a different question: "what happens when things go wrong or happen more than once?" — retry semantics, idempotency, duplicate-request handling, leases/ownership, and failure classification. Per the same standalone discipline as every prior sub-phase: contracts, semantics, and deterministic in-memory reference implementations only; no live Redis/PostgreSQL-backed store, no distributed lease coordination, no live scheduler — all named for Phase 9g.

## Decision

**1. Idempotency and duplicate-request handling share one mechanism: `ExecutionIdempotencyStore` (`ExecutionIdempotency.ts`) plus `ExecutionOrchestrator.runIdempotent()`.** `reserve(key, executionId)` is an atomic check-and-set contract — a real distributed implementation (Phase 9g) would back it with a Redis `SET key value NX` or a SQL unique-constraint insert; the in-memory `InMemoryExecutionIdempotencyStore` given here is a genuine, usable single-process implementation, not a test double. `runIdempotent()` creates the Execution, reserves the key, and — if the key was already held by a *different* Execution — loads and returns *that* Execution instead of creating a second one. A real duplicate command is a lookup of the first orchestration, not a second one. The default, `NoOpExecutionIdempotencyStore`, always succeeds its own reservation (no deduplication), matching every existing caller's current, unchanged behavior — an explicit, visible default, not a silent absence of a check (the same principle `ADR-044` already established for `AllowAllExecutionAuthorizationPolicy`, and the mandatory-version-concurrency reconciliation earlier in this engagement learned the hard way).

**2. Failure classification (`ExecutionFailureClassification.ts`) is a judgment call about a failure *reason string*, not new structural state on the `Execution` aggregate.** `ExecutionFailureClassifier.classify(execution): 'transient' | 'permanent' | 'unknown'` is re-derivable at any time from what `transitionHistory` already persists. `DefaultExecutionFailureClassifier` is a real, usable default: `TIMED_OUT` is always `'transient'` (a deadline being too short says nothing about whether the work itself is impossible); `FAILED` is classified by pattern-matching the most recent transition's `reason` against known transient-failure language (connection/network/timeout/rate-limit/unavailable); anything else defaults to `'permanent'` — the conservative choice, since an unrecognized failure reason is not assumed safe to retry. No field was added to `ExecutionTransitionRecord`/`ExecutionProps` — `Execution.ts` remains exactly as `ADR-039`/`ADR-041`/`ADR-044` scoped it.

**3. Retry eligibility (`ExecutionRetryPolicy.ts`) is a separate decision from retry *mechanics*, which `ADR-040`/9b/9c already built.** `ExecutionOrchestrator.retryIfEligible(original, { attempt })` classifies the failure, asks an injected `ExecutionRetryPolicy.shouldRetry({ execution, failureClass, attempt })`, and only calls the existing `retry()` if it says yes. `attempt` is supplied by the caller, not derived internally: `Execution.childExecutionIds` mixes strict-child and retry-child uses (a workflow's own step children vs. retry attempts), so counting retries by walking that array would silently miscount whenever both uses appear on the same Execution — an honest limitation, not papered over with a plausible-looking but fragile derivation. The default, `NeverRetryPolicy`, never retries — matching every existing caller's current behavior (nothing today calls `retry()` automatically) and, unlike the permissive authorization default, chosen specifically because "never auto-retry" is the conservative, safe default for a decision with real operational consequences (an inappropriate or unbounded retry loop). `MaxAttemptsRetryPolicy` is a real, usable alternative: retries only `'transient'` failures, up to a caller-configured attempt cap.

**4. Ownership is a time-bounded lease (`ExecutionLease.ts`), integrated at `ExecutionOrchestrator.resumeOwned()`.** The contract matches the shape proposed when 9f's scope was first raised (`acquire`/`renew`/`release`, with expiry checked against an injected `Clock` rather than a separate `expire()` call — reusing `ADR-044`'s own deterministic-testability seam). `acquire()` succeeds if unclaimed, expired, or already held by the same owner (idempotent re-acquisition); it throws the pre-existing `ConflictError` (`DomainError.ts`, previously unused in this package) if a different, still-valid owner holds it. `resumeOwned()` acquires before `resume()`ing and releases afterward (in a `finally`, so a thrown error still releases the lease) — a `ConflictError` from a contested lease is allowed to propagate, since "someone else is already driving this forward" is the caller's problem to handle, not something to swallow. Ownership integration was deliberately scoped to `resume()`, not `run()`: a brand-new Execution's id is freshly generated and uncontested by construction, so lease contention only becomes meaningful for re-driving an *existing*, possibly-contended Execution forward (the real scenario: multiple worker processes racing to pick up the same WAITING Execution). `InMemoryExecutionLeaseStore` is the default (not a no-op), since calling `resumeOwned()` at all signals intent to enforce ownership.

## Consequences

- `ExecutionOrchestrator`'s constructor gained four more additive, optional `opts` fields (`idempotencyStore`, `leaseStore`, `failureClassifier`, `retryPolicy`) — every existing call site continues to work unchanged, all defaulting to real, safe, currently-matching behavior.
- `run()` was refactored to extract a shared `driveNewExecution()` private helper, reused by the new `runIdempotent()` — an internal refactor with no observable behavior change for `run()` itself (re-verified by the full existing test suite passing unchanged).
- A real distributed idempotency store, a real distributed lease store, live scheduler-driven retry backoff (`ExecutionRetryPolicy.retryDelayMs()` is defined but not enforced by anything in this standalone phase), and cross-process lease coordination are explicitly out of scope — Phase 9g's job.
- Failure classification's pattern-matching heuristic is a real, but not exhaustive, default — a future, more precise classifier (e.g. one consulting a provider-specific error taxonomy) can be injected without changing the contract.

## Implementation status — Complete for 9f-2's own (standalone) scope; no live idempotency/lease backend or scheduler touched

New files: `ExecutionIdempotency.ts` (`ExecutionIdempotencyStore`/`NoOpExecutionIdempotencyStore`/`InMemoryExecutionIdempotencyStore`), `ExecutionLease.ts` (`ExecutionLease`/`ExecutionLeaseStore`/`InMemoryExecutionLeaseStore`), `ExecutionFailureClassification.ts` (`ExecutionFailureClassifier`/`DefaultExecutionFailureClassifier`), `ExecutionRetryPolicy.ts` (`ExecutionRetryPolicy`/`NeverRetryPolicy`/`MaxAttemptsRetryPolicy`) — all exported from `packages/domain`'s root `index.ts`. `ExecutionOrchestrator.ts` extended: `runIdempotent()`, `retryIfEligible()`, `resumeOwned()`, and the `driveNewExecution()` refactor. Verified, not assumed:

- Real `tsc --strict` typecheck (scratch-toolchain pattern) — clean across the whole `execution/` package, including the four new files and the new test file.
- Real `vitest` run — **132/132 tests passing** across the whole `execution/` package (16 new, in `ExecutionReliability.test.ts`): NoOp-default unchanged behavior, real duplicate-key deduplication (returning the existing Execution), distinct-key non-collision, the `DuplicateCommandError` edge case (reserved key whose owner cannot be loaded), `NeverRetryPolicy`'s real default behavior, `MaxAttemptsRetryPolicy` retrying a transient failure under the cap and declining once the cap is reached or the failure is classified permanent, `DefaultExecutionFailureClassifier`'s TIMED_OUT-always-transient and non-terminal-is-unknown rules, `resumeOwned()`'s acquire-then-release cycle (confirmed via `currentLease()` returning `undefined` afterward), a contested lease correctly raising `ConflictError`, expired-lease reclaim, `renew()`'s same-owner-succeeds/different-owner-throws behavior, and `release()`'s no-op-for-non-holder behavior.
- Scratch verification artifacts removed after the run.
- Not yet done, and not claimed as done: any real Redis/PostgreSQL/etcd-backed idempotency or lease store; distributed lease coordination across processes; a live scheduler enforcing `retryDelayMs()` before re-invoking `retry()`; a more precise, provider-taxonomy-aware failure classifier; Phase 9g's live runtime wiring of any Phase 9 deliverable to date.
