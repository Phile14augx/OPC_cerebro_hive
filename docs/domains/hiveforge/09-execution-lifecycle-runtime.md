# HiveForge Masterplan — Phase 9: Execution Lifecycle Runtime

**Status:** Proposed. `08-ROADMAP.md` (Phase 8) explicitly named "Phase 9" as the place new capability work belongs, rather than being quietly absorbed into the closing phase's deferred-roadmap list — this is that phase. Unlike Phases 1–8, which were architecture-planning-first, this phase begins from a completed **implementation review** (`audit/SLICE-5-EXECUTION-LIFECYCLE-REVIEW.md`) rather than from a clean slate — every claim about the current state below is evidence-backed against real code, not a fresh architectural proposal made in a vacuum.

## Context

`audit/SLICE-5-EXECUTION-LIFECYCLE-REVIEW.md` (an inventory-and-analysis pass, not a HiveForge slice that produced new contracts) established that this repository's execution model — the runtime path from "a request to run an agent or workflow" through "that execution's outcome is durably known" — does not exist as a coherent whole. Concretely, and load-bearing for everything below:

- **No single execution aggregate**: six independent representations exist (`packages/database`'s `WorkflowExecution`/`AgentExecution`, `packages/db`'s differently-shaped and enum-backed equivalents, `packages/domain`'s `AgentExecutionContext`, `services/swarm-runtime`'s mocked `TaskDAG`, and `apps/platform`'s client-only Studio simulator), none sharing an ID space or status vocabulary.
- **No enforced state machine**: the one live write (`WorkflowExecution.status = 'RUNNING'`) is never transitioned again by any code path.
- **No real orchestrator**: `apps/platform-api`'s `runtime.routes.ts` (the component named for this role) is fully mocked.
- **Persistence is non-authoritative**: the one live agent-execution path (`conversations.routes.ts` → `AgentRuntimeService`) persists nothing at all — explicitly deferred per that code's own comment.
- **Lifecycle events are not emitted anywhere live**: HiveForge's own Slice 3 event contracts (`packages/domain-model`) have zero consumers; `packages/domain`'s real event-publishing code (`WorkflowApplicationService`/`AgentApplicationService`) is unreachable dead code; the one working implementation of the correct event pattern lives entirely inside a disconnected client-side simulator.
- **Policy/cancellation don't reach the execution boundary**: `ADR-038`'s policy engine is architecturally sound but has zero live callers; `AgentExecutionContext`'s `policies` field and `cancellationToken` are populated with hardcoded empty/inert values in the one real call site.
- **The one thing that does work**: provider execution itself (`AIGatewayLLMProvider`, `ToolRuntimeToolProvider`) is correctly execution-only, single-call, no orchestration logic — this is the extension point everything else in this phase builds outward from, not something this phase needs to fix.

This phase treats those six gaps as **one missing capability, not six independent backlog items** — per the review's own closing analysis, persistence, events, and policy/cancellation cannot become authoritative until an aggregate and a state machine exist for them to attach to. Sequencing below reflects that dependency, not an arbitrary priority order.

## Governing invariant

**Exactly one canonical `Execution` aggregate exists, and it is the only authoritative execution identity in the platform.** Every execution record — whether it originates from a workflow, an agent, a tool invocation, an evaluation run, a scheduler, or any future runtime component — references that same identity and lifecycle. Concretely:

- One execution ID (not a per-subsystem id space, and not `AgentExecutionContext`'s current `traceId`-as-execution-id substitute, per the review's finding that this identifies nothing once the HTTP response is sent).
- One lifecycle state (9b's state machine, not a parallel status vocabulary per subsystem).
- One state machine (one legal-transition graph, enforced in one place).
- One persistence model (9d, not a second schema for "agent executions" vs. "workflow executions" the way `packages/database` and `packages/db` currently diverge).
- One event stream (9e, emitting from the one state machine, not re-derived per subsystem).

This is the standard every later sub-phase is measured against, and the specific thing this phase exists to prevent recurring: the six-way fragmentation `audit/SLICE-5-EXECUTION-LIFECYCLE-REVIEW.md` found did not happen all at once — it accumulated one reasonable-seeming per-subsystem decision at a time (an `AgentExecution` table here, a differently-shaped `WorkflowExecution` there, a client-side simulator with its own event vocabulary elsewhere). Holding every sub-phase to this one invariant is what keeps that from happening again as new capabilities (schedulers, tool invocations, evaluation runs) get built on top of Phase 9's output.

## Scope: six sequenced sub-phases

**9a. Canonical `Execution` aggregate and unified status vocabulary.** Defines one authoritative identity and status model, replacing the six-way fragmentation the review found. This does not mean deleting `packages/db`'s schema or `packages/database`'s — it means deciding, with evidence, which one (or what new one) becomes canonical, and what happens to the others (migrate, adapter-wrap, or formally retire). `packages/db`'s enum-backed `ExecutionStatus` (`QUEUED`/`RUNNING`/`WAITING_FOR_HUMAN`/`COMPLETED`/`FAILED`/`TIMEOUT`/`CANCELLED`) is real, better-designed than the live schema's plain strings, and stranded in an unwired tree (`services/platform-api`, per `audit/SERVICES-PLATFORM-API-CLASSIFICATION.md`) — this sub-phase's design work should read that schema before inventing a new one, consistent with this masterplan's "inventory before contracts" discipline from Slices 1–4.

**9b. Lifecycle state machine with validated transitions.** Fixes the legal transition graph (which states can reach which others, whether illegal transitions are rejected or silently allowed) and closes the specific gap the review found: a `WorkflowExecution` row that is created and then never transitions again. Must explicitly address cancellation (represented in the type today, inert in practice) and resumability (`ExecutionCheckpoint`'s schema already exists, unused — evaluate reusing its shape: `contextSnapshot`/`variables`/`pendingActions`/`eventOffset`, rather than designing a second one).

**9c. Production orchestrator, built around the 9a/9b aggregate.** Replaces `runtime.routes.ts`'s mocked handlers with a real component that coordinates execution and invokes providers — but does not itself become a provider or duplicate provider-execution logic (the "providers execute, orchestrators coordinate" invariant the review confirmed already holds and must keep holding). Whether this absorbs `AgentRuntimeService`'s existing while-loop, wraps it, or replaces it is a design decision for this sub-phase, not decided here.

**9d. Durable persistence and recovery checkpoints.** Only meaningful once 9a/9b exist — persists execution state through the canonical aggregate, and evaluates reusing `packages/database`'s already-designed (currently unused) `ExecutionCheckpoint` model for resumability rather than building a second checkpoint mechanism from scratch.

**9e. Lifecycle event emission from every state transition.** Wires real event publication into every 9b transition. Must resolve, not duplicate further, the fact that a correct event-shape (`ExecutionCreated → ...Scheduled → ...Started → ...Progress → ...Completed`/`Failed`/`Cancelled`) already exists twice in this repository — once as HiveForge's own unused `HiveDomainEvent`/`HiveEventBus` contracts (`packages/domain-model`, Slice 3), once as a working implementation inside `apps/platform`'s disconnected Studio simulator. This sub-phase's job is to make ONE of these (most likely `packages/domain-model`'s, since it's this masterplan's own contract and already `Hive`-prefixed/disambiguated per Slices 1–3's naming discipline) the real, live implementation — not to design a third.

**9f. Policy and cancellation integration into the execution pipeline.** Wires `ADR-038`'s policy engine (`hiveshield-policy`/`policy-core`) into the 9c orchestrator at the boundary the Slice 5 review confirmed is architecturally available (`HierarchicalPolicyEngine.evaluate()` is already provider-agnostic — the gap is that nothing calls it, not that it can't be called). Also resolves the five-way policy/authorization fragmentation the review found (`@cerebro/auth` RBAC, `packages/domain`'s own `PolicyEngine`, `policy-core`/`hiveshield-policy`, `packages/engineering-review`'s `AIGovernanceEngine`) to the extent it's reachable from the execution pipeline specifically — a full repository-wide policy-mechanism consolidation is a larger governance question this sub-phase does not have to fully resolve, only the slice of it that touches execution.

## Exit criteria

Each sub-phase's completion is judged against an objective condition, not a subjective "good enough" call — this is what makes the phase's own future conformance-checking tractable, the same way the masterplan's ADR-reference/naming-drift/evidence-status gates are tractable because they're mechanical, not judgment-based:

| Sub-phase | Exit criteria | Verification method |
|---|---|---|
| 9a | A single canonical `Execution` aggregate is adopted across the runtime — every execution-producing subsystem (agents, workflows, and whatever else exists at the time) references the same identity, not a per-subsystem one. | Architecture review (confirming no subsystem retains a competing identity) + schema validation (a real migration/consolidation against `packages/database`'s and `packages/db`'s existing schemas, not just a new type on paper). |
| 9b | All lifecycle transitions are validated through one state machine — an illegal transition is rejected, not silently allowed, and no execution can be created and then never transitioned again (closing the specific gap the review found). | Unit tests (each legal/illegal transition pair, mirroring the discipline already used for `HierarchicalPolicyEngine.test.ts`'s explicit-rule-per-test style) + integration tests against the real persistence layer from 9d. |
| 9c | Every provider invocation passes through the orchestrator — no execution path calls a `HiveProviderExecutor`-shaped provider directly, bypassing 9c's coordination layer, the same bypass pattern the review found in `workflows.routes.ts` (a bare DB insert with no orchestrator involved at all). | Runtime conformance tests — a repo-wide check (in the spirit of `hiveforge_conformance_check.py`) that no route/handler imports a provider package directly without going through the orchestrator, plus real end-to-end tests of at least one full execution. |
| 9d | Execution state survives restart and recovery — an in-flight execution's state can be reconstructed after a process restart, using 9a's aggregate and (per 9d's own scope note) evaluating reuse of `packages/database`'s existing `ExecutionCheckpoint` shape. | End-to-end resilience tests — actually kill and restart the process mid-execution in a test environment and assert the execution resumes or fails cleanly, not just a unit test of the checkpoint-writing code in isolation. |
| 9e | Every lifecycle transition emits a canonical event — no transition happens silently, and the event stream is sufficient on its own to reconstruct execution history (closing the review's specific finding that zero events are emitted anywhere in the live system today). | Event contract tests — assert, for every 9b transition, that exactly one well-formed event (against whichever of `HiveDomainEvent`/the Studio simulator's shape is chosen as canonical per 9e's scope note) is published, and that replaying the stream reconstructs the execution's final state. |
| 9f | Authorization, policy evaluation, and cancellation are enforced during execution — not merely available to be called, per the review's distinction that `ADR-038`'s engine is architecturally sound but has zero live callers today. "Enforced" means a denied/cancelled execution cannot proceed, verified by a real test, not merely wired and untested. | Security and integration tests — a real test asserting a `Deny`/`HumanApproval` decision from `HierarchicalPolicyEngine` actually halts execution before a provider is invoked, and a real test asserting a populated `cancellationToken` actually stops an in-flight execution (closing the review's finding that this token is currently always `undefined` in the one live path). |

## Explicit sequencing dependency

9a and 9b are prerequisites for 9c–9f, not independent workstreams that can run in parallel with them — per the review's own finding, persistence/events/policy "cannot become authoritative even if implemented individually" without an aggregate and state machine underneath them. 9c depends on 9a/9b directly (an orchestrator needs something to orchestrate the state of). 9d and 9e can proceed in parallel with each other once 9c exists, since persistence and event emission are both downstream of "a real transition happened," not of each other. 9f depends on 9c (there must be an execution pipeline to insert a policy checkpoint into).

## Non-goals (this phase)

No new provider work (the provider layer already works, per the review — this phase is explicitly the layer immediately above it). No repository-wide consolidation of every policy/authorization mechanism found across the whole codebase (`change-core`'s CAB approvals, `federation-core`, etc. — those remain `audit/HIVEFORGE-SLICES-1-4-GOVERNANCE-BACKLOG.md` items, out of scope here). What the validated transition graph looks like is not decided here — that is 9b's design output. (Which of `packages/database`/`packages/db` is canonical, and the new `Execution` aggregate's exact field list, are now decided — see `ADR-039`, drafted after 9a's implementation was built and verified, not before.) No ADR was written by this scoping document itself; `ADR-039` was drafted separately once there was real, verified implementation evidence to decide from, and 9b's own design work is expected to produce at least one further ADR for transition legality.

## ADR references

`ADR-039` (Canonical Execution Aggregate) — drafted once 9a's implementation existed and was verified, not before, per the same discipline already applied to `ADR-038`. It fixes 9a's own scope only: identity (`ExecutionId`), status vocabulary (`ExecutionStatus`), aggregate shape (parent/child vs. contributor references, metadata, timestamps), and the `ExecutionRepository` contract.

`ADR-040` (Execution Lifecycle State Machine) — drafted once 9b's implementation existed and was verified, same discipline. Fixes the canonical transition graph over `ADR-039`'s existing vocabulary (no new statuses), transition metadata/history, monotonic-timestamp and reason-required invariants, retry-as-child-execution semantics, and the transition→canonical-event mapping (`transitionTo()` returns the event; does not publish it). Before drafting, a premise that this sub-phase should treat `packages/engineering-review`'s `SandboxStateMachine`/`ExecutionPlanner` ("M26.7–9") as prior sub-phases of this same lineage was checked against the code and found not to hold — that runtime is a separate bounded context with its own status vocabulary, read here only as prior art for the "graph + reject-if-illegal" shape, not merged with or migrated onto by this ADR. `ADR-022` (Resource Lifecycle State Machine) was also read as a related but distinct precedent for the same reason.

`ADR-041` (Standalone Production Orchestrator) — drafted once 9c's implementation existed and was verified. Before building it, whether to build the orchestrator standalone (zero live wiring, matching 9a/9b's own pattern) or wire it directly into the live system was raised explicitly and decided: standalone for this pass, live wiring deferred to a separate future milestone once Phase 9d gives it a real `ExecutionRepository` to inject. Fixes the orchestrator's coordination-only responsibility (re-affirming "providers execute, orchestrators coordinate"), the new `ExecutionProviderPort`/`ExecutionEventSink` seams, and `retry()`/`resume()` behavior built on `ADR-040`'s transition graph and retry semantics. Idempotency, authorization, cancellation, and timeout detection are named as explicitly out of scope, not silently absent.

`ADR-042` (Standalone Execution Persistence, Checkpointing, and Replay) — drafted once 9d's implementation existed and was verified. Same standalone-vs-live question asked and decided the same way: a real `ExecutionRepository` implementation (`InMemoryExecutionRepository`) plus checkpointing and deterministic replay, built without touching `packages/database`'s live schema — `ADR-039`'s deferred canonical-schema decision remains exactly as deferred as before. Fixes the `ExecutionSnapshot` serialization boundary, an additive optimistic-concurrency parameter on `ExecutionRepository.save()`, the `ExecutionCheckpointStore` contract (separate from `save`/`findById`), and `replayExecution()` as the executable proof of `ADR-040`'s deterministic-replay claim. Crash recovery is demonstrated via the existing (unchanged) `ExecutionOrchestrator` public API, not a new integration surface.

Event publishing and policy/cancellation enforcement remain 9e/9f's own future ADRs, not fixed here.

## Architectural Impact

This is the first HiveForge masterplan phase whose primary input is a **runtime-completeness gap**, not an architecture-planning exercise or a naming/collision reconciliation (Slices 1–4's mode). It does not change any decision fixed in Phases 0–8 — it adds a new phase in the sense `08-ROADMAP.md` §"Explicitly not proposed by this masterplan" anticipated ("If you want these designed, that's new scope for a Phase 9"). No existing ADR is amended by this document. The dependency map in `08-ROADMAP.md` §1 should be updated to add this phase once its own ADR(s) exist and can be cited precisely; not done here since none exist yet.
