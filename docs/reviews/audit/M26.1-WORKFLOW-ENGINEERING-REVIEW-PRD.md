# M26.1 — Workflow Engineering Review

## Product Requirements Document (Draft)

**Status:** Proposal. Product decision made (Workflow Engineering Review, not Release Engineering Review — see `M26.1-ENGINEERING-REVIEW-ASSISTANT-BRIEF.md` for the evidence behind that choice). This document defines product behavior only — no classes, APIs, or data models. Those come in Phase 3 onward, after this PRD is agreed.

---

## Purpose

Give workflow engineers, platform engineers, and architects an evidence-backed engineering review of a workflow before it's approved — surfacing architectural concerns, duplication, and convention violations that today only a human reviewer would catch, if anyone catches them at all. The assistant recommends; a human still approves. This doesn't replace the existing publish-time policy check (`CanPublishWorkflow`) — that answers "is this allowed"; this answers "is this a sound engineering change."

**Governing invariant**: Engineering Review is advisory. It informs publication decisions but does not determine publication authorization. Authorization remains the sole responsibility of the existing policy evaluation (`CanPublishWorkflow`) and any human approval processes the organization defines. If a review could block publication, it would become a second authorization mechanism sitting alongside the existing one — the same kind of overlapping authority this audit repeatedly found and had to reconcile elsewhere in the platform (two Helm generations, four independent policy engines, two services both calling themselves "the platform API"). Keeping these two authorities — authorization and engineering judgment — separate is a deliberate design choice, not a placeholder to revisit casually. A future milestone may intentionally introduce configurable enforcement, but that would be a new, explicit decision, not a drift from this one.

## Users

- **Workflow engineers** — the people authoring and publishing the workflow, the primary recipients of review findings.
- **Platform engineers** — responsible for the shared capability graph the workflow draws on; care most about duplication and misuse of existing capabilities.
- **Architects** — care about structural/complexity concerns that individual workflow engineers may not have visibility into across the whole platform.

Not yet in scope as a distinct audience: security reviewers, compliance reviewers. If those turn out to need materially different findings, they're candidates for later milestones (M26.2+), not this one.

## Trigger

Review runs when a workflow author **publishes a new version** — i.e., at the existing `WorkflowApplicationService.publishVersion()` call site, alongside the policy check and validation that already happen there. Not on every draft edit, and not continuously during editing — this is a checkpoint at the publish moment, not an always-on linter.

Whether it should also be runnable on demand, ahead of publishing (so an author can get feedback before committing to a publish attempt), is open — see Non-goals and Open Questions.

## User Journey

```
Workflow engineer edits a workflow (nodes/edges)
        ↓
Author publishes a new WorkflowVersion
        ↓
Existing checks run first, unchanged:
  - CanPublishWorkflow policy check
  - WorkflowValidator structural validation
        ↓
Engineering Review runs
  - reads the new version's graph (nodes/edges)
  - compares against the prior version, if one exists
  - compares against the platform's known capability graph
  - produces findings with citations back to what it read
        ↓
Publish completes regardless of review outcome (review is advisory,
not a gate, for this milestone — see Success Metrics/Non-goals)
        ↓
Findings are attached to the published version and visible to the
author, platform engineers, and architects
        ↓
A human decides whether the findings warrant a follow-up change
```

## Inputs

- The new `WorkflowVersion`'s graph: nodes (name, type, config) and edges (source/target, condition) — the same data `WorkflowRepository.publishVersion()` already persists.
- The immediately prior version of the same workflow, if one exists, for comparison (duplication/drift relative to the workflow's own history).
- The platform's capability registry, so the review can flag when a workflow implements something a registered capability already does.
- Existing policy definitions, if a ruleset for "engineering convention" (as opposed to publish authorization) is agreed to exist — which of the platform's several policy-engine-shaped systems supplies this, if any, is an open product/architecture question, not decided in this PRD.

## Outputs

- A set of findings, each with: what was flagged, why, and a citation to the specific part of the workflow graph (or comparison target) that triggered it — mirroring the evidence-with-citations standard this audit itself was held to.
- An overall recommendation: **clear**, **flagged** (findings exist, author should look, publish not blocked), or **needs attention** (findings serious enough that a human should look before treating the version as final) — three states, not a numeric score, to avoid implying false precision.
- No automatic blocking of publish in this milestone (see Non-goals). The review attaches to the version; it does not gate it.

## Success Metrics

Not fully defined — needs your input to finalize thresholds, but the categories:

**Quality**
- Agreement with senior engineering reviewers on flagged findings.
- Precision of surfaced findings (signal, not noise).
- False-positive rate.
- Missed-issue rate, where measurable.

**Adoption**
- Reviews requested per published workflow (once on-demand review, if added later, makes this meaningful).
- Percentage of recommendations actually viewed.
- Recommendation acceptance rate.

**Outcome**
- Correlation between review findings and later operational issues.
- Reduction in post-publication defects.
- Reduction in manual review effort / time saved during workflow review.

**Explainability** — a core differentiator, not an afterthought: engineering reviewers can trace every finding and recommendation back to its supporting evidence, without implicit reasoning or hidden decision logic. This is measurable (e.g., "can a reviewer always locate the specific graph element or comparison that produced a given finding?") and should hold from the first release, not be treated as a later polish item.

Setting numeric thresholds for any of these now, before real usage exists, would be arbitrary — these are the categories to instrument for, not committed targets.

## Non-goals

- **Not a publish gate.** It does not block publishing in this milestone, regardless of finding severity. Whether a future milestone changes this is explicitly out of scope here.
- **Not a replacement for `CanPublishWorkflow`** or `WorkflowValidator` — those remain the authorization/structural-correctness checks; this is a third, additive step.
- **Not Release Engineering Review.** This PRD covers workflow publication only. CI/CD release review (per the audit's finding that these are two unrelated systems) is a separate, later milestone if pursued at all.
- **Not security, compliance, or cost review.** Those are candidate future review types under a shared framework, not part of M26.1's scope.
- **Not an autonomous approval mechanism.** No finding this produces results in an automatic action beyond being recorded and shown to a human.

## Open Questions carried into Phase 3 (Architecture Review)

1. Should review be runnable pre-publish (draft-time, on demand), or strictly at publish time as scoped above?
2. Which existing policy-engine-shaped system, if any, supplies the "engineering convention" ruleset — or does this need one of its own, and if so, is that a fifth competing policy engine or a genuine specialization?
3. Does a "flagged"/"needs attention" finding ever need to reach anyone besides the author (e.g., does an architect get notified proactively, or only see it if they look)?
4. At what point, if ever, should this evolve from advisory into a publish gate — and who makes that call?

These are architecture and product-detail questions to resolve in the next phase, not blockers to agreeing this PRD's Purpose, Users, Trigger, Inputs, Outputs, and Non-goals as currently written.
