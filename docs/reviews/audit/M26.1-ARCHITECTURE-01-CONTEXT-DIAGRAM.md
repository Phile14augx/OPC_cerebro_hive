## Systems in scope (this diagram)

- **Workflow Studio / Workflow Author** — where the reviewed artifact originates. Not modified by M26.1; the author's experience changes only in that findings become visible after publish.
- **`WorkflowApplicationService.publishVersion()`** — the existing orchestration point. Engineering Review is a new step alongside the three that already exist there (authorize, validate, persist). Per ADR-001/ADR-002, it runs *alongside*, not *instead of* or *before-and-gating* any of the three.
- **`CanPublishWorkflow` policy check, `WorkflowValidator`, `WorkflowRepository`** — existing systems, referenced here only to show where the new step sits relative to them. None are modified by this milestone.
- **Engineering Review (M26.1)** — the new capability. **Responsibility**: evaluate a workflow version using immutable evidence and produce evidence-backed review artifacts. Reads the published graph, the prior version (if any), and the capability registry. Produces four distinct output artifacts, not one undifferentiated "result": **Evidence** (exists independently, the primary artifact per ADR-003), **Findings** (derived from evidence), **Recommendations** (derived from findings), and a **Review Summary** (a presentation object over the other three, not a separate source of truth). Per ADR-001, none of these ever changes the outcome of the authorize/validate/persist steps.
- **Audit Logger, Outbox Publisher** — existing systems already invoked by `publishVersion()`. Shown because Engineering Review's own findings-attachment step is a plausible (not yet decided) place to reuse one or both, rather than inventing parallel logging/eventing — a Phase 3/4 question, not resolved here.
- **Workflow engineers, platform engineers, architects** — the PRD's Users, consuming findings after they're produced.

## Systems explicitly out of scope (per ADR-004 and the PRD's Non-goals)

- `release-train.yml`, `docker-build.yml`, ArgoCD, and the rest of the CI/CD release pipeline — no relationship to this diagram at all.
- `apps/studio/platform` and `apps/studio/agentos` — unrelated deployment targets (per `DEPLOYMENT-ARCHITECTURE-DISCOVERY.md`), not part of the workflow-publication lifecycle this diagram covers.
- The platform's other `PolicyEngine`-shaped implementations (`packages/policy`, `packages/policy-core`, `apps/studio/platform`'s kernel policy engine) — not shown, because whether any of them supplies an "engineering convention" ruleset is still an open question (PRD Open Question 2), not a decided input.

## What this diagram deliberately does not answer

- What "Engineering Review" is made of internally (services, modules, contributor boundary per ADR-005) — Phase 2 (Bounded Context) and Phase 3 (Domain Model).
- Where findings/evidence are stored, and under what durability/versioning guarantees — Phase 5 (Persistence Model).
- What the public interface into this system looks like — Phase 4 (Service Boundaries).

This context diagram's only job is to confirm the shape of the *existing* lifecycle Engineering Review attaches to, and to make explicit what it does and doesn't touch, before any internal structure is designed.
