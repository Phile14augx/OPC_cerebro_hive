# Contributor Interface Reconciliation (feeds M26.3 ADR)

**Status:** Decision made, migration path defined. This is not the M26.3 ADR itself — task #75 formalizes this into ADR form. This document exists so that decision has real code evidence behind it before it's written up.

## The two interfaces, side by side

**`ports/IReviewContributor.ts` (baseline, governs per ADR-005):**
```ts
interface IReviewContributor {
  readonly contributorId: string;
  readonly displayName: string;
  readonly version: string;
  readonly category: string;
  execute(context: ReviewContext): Promise<ContributorResult>;
}
// ContributorResult: { contributorId, status: 'succeeded'|'failed'|'skipped', evidence: EvidenceReference[], findings: ReviewFinding[], error? }
```

**`contributors/sdk/ContributorContext.ts` (the competing definition):**
```ts
interface IReviewContributor {
  readonly id: string;
  readonly version: string;
  execute(context: ContributorContext): Promise<any>;
}
// ContributorContext: { snapshotId, semanticChangeset: any, policyVersion, reviewConfiguration: any, cancellationToken: any, logger: any }
```

## Decision: `ports/IReviewContributor.ts` is canonical

Direct code evidence, not just doc comparison:

1. **Return typing.** The baseline returns a typed `ContributorResult` with a closed `ContributorStatus` union. The `sdk/` version returns `Promise<any>` — there is no structural guarantee at all about what a contributor hands back. `ARCHITECTURE-06`'s failure-isolation principle depends on the status/result shape being reliable; `any` defeats that at the type level.

2. **Orchestrator bypass, confirmed in code.** `EngineeringReviewOrchestrator.safeExecute()` is the governed execution path: it calls `contributor.execute(context)` inside a try/catch that converts a thrown exception into a structured `{ status: 'failed', ... }` result, then the orchestrator does the two-pass evidence/finding composition (`addEvidence` then `addFinding`, in that order, for lifecycle reasons documented in the orchestrator itself). `InProcessContributorHost.executeAgent()` does something similar in shape (try/catch around `agent.execute()`) but is a wholly separate object with no connection to `EngineeringReviewOrchestrator`, no dependency-DAG ordering, and no participation in the aggregate's evidence/finding lifecycle. A contributor run through the `sdk/`/`InProcessContributorHost` path never reaches `EngineeringReviewReport` at all. That is a direct instance of the boundary `ARCHITECTURE-06` names explicitly: a contributor must never bypass the orchestrator.

3. **ADR-005's own test for this exact situation.** ADR-005 states that if a future contributor requires a structural change to the framework, that signals the boundary was misdrawn and should be revisited — not special-cased. The `sdk/` interface is precisely a special case introduced instead of extending the governed interface. Nothing about Security/Compliance/Cost/Reliability contributors requires `semanticChangeset: any` or a second execution host; `ReviewContext` (snapshot, workflow ids, workflow summary) plus category-specific evidence-gathering inside `execute()` is sufficient.

## Migration path

1. **`contributors/sdk/ContributorContext.ts`** — remove. Nothing outside `InProcessContributorHost` and the four stub agents depends on it (confirmed: it's not imported by the orchestrator, repository, or any infrastructure adapter).
2. **`InProcessContributorHost.ts`** — remove as a standalone execution path. If it contains logic worth keeping (state tracking `PENDING → RUNNING → COMPLETED`, mentioned in a comment but not actually implemented — the code only has a try/catch, no state machine yet), that logic should be added to `EngineeringReviewOrchestrator.safeExecute()` directly, not kept as a second host.
3. **`SecurityReviewAgent`, `ComplianceReviewAgent`, `CostReviewAgent`, `ReliabilityReviewAgent`** — rewrite each to implement `ports/IReviewContributor.ts`: add `contributorId`/`displayName`/`category`, change `execute(context: ReviewContext)`, return real `ContributorResult` shape. Each currently returns a hardcoded `{ findings: [], recommendations: [], status: 'COMPLETED' }` with a comment claiming delegation to analyzer classes that don't exist (`EdgeEncryptionAnalyzer`, `TopologyExposureAnalyzer`, `IAMAnalyzer`, and their Compliance/Cost/Reliability equivalents) — those either need to be built for real or the stub needs to honestly report `status: 'skipped'` with an explanatory reason rather than claiming completion with zero findings, which is indistinguishable from "ran and found nothing."
4. **Registration/ordering** — once rewritten, these four register the same way `ArchitectureReviewContributor` does today: passed into `EngineeringReviewOrchestrator`'s constructor as part of the `contributors: readonly IReviewContributor[]` array. Dependency-DAG ordering (`ARCHITECTURE-06`, deferred to Slice 6 per the orchestrator's own comments) is still not built — for now these run in sequence like the existing single contributor does; that's a pre-existing scope gap, not something this migration needs to solve.
5. **`ContributorE2E.test.ts`** — once at least one of the four is rewritten, replace its current content (stub-status assertion + empty placeholder) with real tests against the rewritten contributor running through `EngineeringReviewOrchestrator`, following the same pattern as `EngineeringReviewOrchestrator.test.ts`'s existing failure-isolation tests.

## What this does not decide

Whether all four contributors get built now, get built incrementally, or get explicitly marked "planned, not yet implemented" in the M26.3 ADR is a scoping call, not an interface call — left to task #75.
