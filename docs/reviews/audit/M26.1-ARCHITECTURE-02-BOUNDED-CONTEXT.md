# M26.1 — Architecture Phase 2: Bounded Context

**Status:** Draft. Builds on Phase 1 (`M26.1-ARCHITECTURE-01-CONTEXT-DIAGRAM.md`). Defines domain responsibilities and ownership boundaries — still not domain objects, aggregates, or interfaces (that's Phase 3), and not services or APIs (Phase 4).

## The bounded context

**Name:** Engineering Review (workflow review contributor, per ADR-005).

**Purpose, restated from the context diagram's responsibility annotation:** evaluate a workflow version using immutable evidence and produce evidence-backed review artifacts.

## What this context owns

- **Evidence** — the record of what was read and compared to produce a finding (per ADR-003, the primary artifact; everything else derives from it). *Refined in Phase 3*: this context owns the evidence *record* (a structured reference/citation into source data — what was read, when, and where), not the underlying source data itself. The workflow graph and capability registry remain owned by their respective contexts, per "What this context does not own" below; this context does not duplicate or take custody of that source data.
- **Findings** — statements derived from evidence.
- **Recommendations** — statements derived from findings.
- **Review Summary** — a presentation object over the above three; not an independent source of truth.
- **The comparison logic** between a new workflow version, its prior version, and the capability registry — i.e., the actual evaluation behavior is this context's responsibility, not something borrowed from elsewhere.
- **The lifecycle of a single review** — from invocation (at `publishVersion()`, per ADR-004) through to a completed Evidence/Findings/Recommendations/Summary set. Whether "lifecycle" implies a stateful aggregate with intermediate states, or a single synchronous computation, is a Phase 3 (Domain Model) question — not decided here.

## What this context explicitly does not own

- **Authorization.** `CanPublishWorkflow` is not part of this context and is never called by it, per ADR-002. This context cannot cause a publish to fail.
- **Structural validation.** `WorkflowValidator`'s responsibility (is the graph well-formed) is separate from this context's responsibility (is the graph a sound engineering change). This context assumes it's being handed an already-structurally-valid graph.
- **The workflow graph itself.** `WorkflowVersion`/`WorkflowNode`/`WorkflowEdge` and their persistence remain owned by `WorkflowRepository`. This context reads them; it does not create, mutate, or version them.
- **The capability registry.** Read-only dependency, owned and evolved elsewhere. This context does not register, deregister, or modify capabilities based on what it finds.
- **Audit logging and eventing infrastructure**, as such. Whether this context reuses the existing Audit Logger/Outbox Publisher or has its own is explicitly still open (flagged in Phase 1); either way, the *infrastructure* for durable logging/eventing is not something this context is introducing or owning — it's a consumer of that infrastructure, however it's ultimately wired.
- **Engineering-convention policy rules**, if those turn out to be a distinct ruleset (PRD Open Question 2). If such a ruleset exists, this context consumes it as an input the same way it consumes the capability registry — it does not define or govern the ruleset itself. Ownership of that ruleset, if it exists, belongs to whichever policy system is chosen to supply it (an open question, not resolved here or elsewhere yet).
- **Presentation/UI.** How findings are displayed to workflow engineers, platform engineers, and architects is a separate concern from producing them.
- **Any other review type.** Security, cost, compliance, or release review (ADR-004, ADR-005) are separate bounded contexts-to-be, sharing a framework with this one but not sharing this context's internals.

## Interfaces to neighboring contexts

Two read-only inbound dependencies, both already established as existing systems in Phase 1:

- **Workflow publication context** (`WorkflowApplicationService`, `WorkflowRepository`) — supplies the new version's graph and the prior version. This context reads from it; it is invoked *by* it (per ADR-004, at the `publishVersion()` call site), not the other way around. This is the one place an anti-corruption layer is worth naming explicitly: this context should not assume it always receives `WorkflowVersion`/`WorkflowNode`/`WorkflowEdge` in their exact current Prisma-model shape — a translation boundary here means a schema change on the workflow-publication side doesn't force a change to this context's internal evidence model, and vice versa.
- **Capability registry** — supplies the set of known capabilities to compare a workflow's implementation against. Same treatment: read through a boundary shaped for this context's own evidence needs, not a direct dependency on the registry's internal representation.

One outbound relationship, not yet fully specified:

- **Findings consumers** (workflow engineers, platform engineers, architects, per the PRD) — this context produces Evidence/Findings/Recommendations/Review Summary; something downstream (a UI, a notification, a query API) consumes them. What that consumption interface looks like is Phase 4 (Service Boundaries).

No relationship, direct or indirect, to: `CanPublishWorkflow`'s internals, `WorkflowValidator`'s internals, the CI/CD release pipeline, `apps/studio/platform`, `apps/studio/agentos`, or the platform's other `PolicyEngine` implementations — consistent with the Phase 1 out-of-scope list.

## Domain services vs. application services (named, not yet designed)

Two distinct kinds of behavior belong in this context, worth distinguishing now so Phase 3 doesn't collapse them into one undifferentiated "review logic" blob:

- **Domain-level evaluation behavior**: the actual comparison logic — what makes a finding a finding, how evidence supports it, how findings roll up into recommendations. This is the part that should be independent of *how* a review gets triggered.
- **Application-level orchestration behavior**: being invoked at the right point in `publishVersion()`, gathering the three read-only inputs, assembling the four output artifacts, and handing them to whatever consumes them next. This is the part that's aware of the surrounding system.

Which specific classes/functions embody each is a Phase 3 question. The distinction itself is a Phase 2 decision: keeping evaluation logic ignorant of its trigger point is what will let a future on-demand/pre-publish review mode (PRD Open Question 1) reuse the same domain logic through a different application-level entry point, rather than requiring a second implementation of the evaluation behavior itself.

## What Phase 2 deliberately does not answer

- Aggregate boundaries and invariants within Evidence/Findings/Recommendations/Review — Phase 3.
- Repository shapes, domain events, persistence guarantees — Phase 3 (aggregates) and Phase 5 (persistence model).
- Concrete interfaces/APIs for the findings-consumer relationship — Phase 4.
- Whether the anti-corruption layers named above are literal adapter classes, a mapping layer, or something else — Phase 3/4.
