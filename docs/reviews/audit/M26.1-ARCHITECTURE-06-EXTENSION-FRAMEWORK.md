# M26.1 — Architecture Phase 6: Extension Framework

**Status:** Draft. Builds on Phase 5 (`M26.1-ARCHITECTURE-05-PERSISTENCE-MODEL.md`). Defines how the architecture admits contributors (per ADR-005) without violating anything established in Phases 1–5. Deliberately does not introduce new domain concepts — where something here would require changing `EngineeringReview`, `Finding`, `Recommendation`, `Manifest`, or `Verdict`, that's a signal it belongs in an earlier phase, not here. This is the "constitution" for every contributor written from here forward, including the one M26.1 ships (Workflow Review) and every future one (Security, Architecture, Reliability, Cost, Compliance, custom).

## 1. Contributor lifecycle

```
Discover
    ↓
Validate
    ↓
Register
    ↓
Resolve
    ↓
Execute
    ↓
Produce ContributorResult
    ↓
Dispose
```

Plugin management (`Discover` → `Register`) is a distinct concern from review execution (`Resolve` → `Dispose`), and this framework keeps them separate: a contributor can be discovered and registered without ever being resolved or executed against a specific review. This mirrors the domain/application-layer split from Phase 3/4 — lifecycle management is infrastructure; a single execution is invoked by the application layer per review.

## 2. Contributor contract

`IReviewContributor` (naming continued from prior discussion) is an architectural contract, not a bare interface. Each contributor declares:

- Contributor ID
- Display name
- Version
- Category (e.g., Workflow, Security, Architecture, Reliability, Cost, Compliance)
- Required vs. optional (whether a review can reach `Published` without this contributor succeeding)
- Execution capabilities (what kinds of evidence/findings it can produce)
- Declared dependencies (see §3)
- Supported workflow types (a contributor need not apply to every workflow)

This metadata belongs to the extension framework's registry, not to the domain model — `EngineeringReview` doesn't know or care which contributors ran; it only holds the `Finding`s, `Recommendation`s, and `Manifest` entries (including a `Contributor Manifest`, per Phase 5) that resulted.

## 3. Ordering and dependency graph

Contributors declare dependencies on each other rather than numeric priorities:

```
Architecture
        ↓
Security
        ↓
Compliance

Cost
        ↓
Finance
```

The framework computes a DAG at registration time and rejects cycles then — not at execution time, when a cycle would be far more expensive to diagnose. Numeric priorities don't scale past a handful of contributors (the exact failure mode this platform's Helm-chart and PolicyEngine duplication findings kept illustrating: implicit ordering that nobody can reason about once enough pieces accumulate); a declared dependency graph keeps the ordering legible as the contributor set grows toward the full roadmap (M26.2–M28).

## 4. Failure isolation

```
Contributor
        ↓
Execution Result
        ↓
Status
        ↓
Findings
        ↓
Evidence
```

Each contributor executes in an isolated boundary. A contributor failure produces a structured `ContributorResult` with a status — it does not throw an exception that propagates across contributor boundaries or aborts the whole review. The orchestrator (not any individual contributor) decides how a required-but-failed contributor affects the review's ability to reach `EvaluationCompleted`/`Published` — that's a governance-policy decision made once, centrally, rather than each contributor implementing its own opinion about how failure should be handled.

## 5. Composition model

How multiple contributors' outputs combine, defined once rather than per contributor:

- Findings are appended — one contributor's findings never replace another's.
- Evidence is additive — the same accumulation rule.
- Confidence is aggregated by a configured strategy (not hardcoded per contributor) — which strategy is a Phase-6-adjacent implementation decision, not specified here, but the fact that aggregation is centrally configured rather than contributor-defined is the architectural commitment.
- Recommendations are synthesized after all contributors execute, by the framework, not by individual contributors. This preserves a single source of recommendation logic (echoing Phase 3's invariant that a `Recommendation` derives from `Finding`s in one consistent way) rather than each contributor producing its own competing recommendation logic — precisely the kind of duplicated authority this audit spent most of its effort reconciling elsewhere in the platform.

## 6. Extension boundaries — what contributors must never do

- Modify reviews.
- Mutate findings from other contributors.
- Publish integration events (that remains the aggregate/application layer's responsibility, per Phase 4's domain/application/integration event split — a contributor producing its own integration events would bypass the translation-step boundary Phase 4 established).
- Write directly to repositories (per Phase 5's repository-responsibility principle — only the `EngineeringReviewRepository` touches the aggregate's persistence, never a contributor directly).
- Bypass the orchestrator.
- Invoke other contributors directly (even ones it declares a dependency on — the framework resolves and sequences dependencies; a contributor calling another contributor's code directly would recreate exactly the ordering/coupling problem §3's DAG exists to prevent).

Everything flows through the orchestrator. This list exists so that as contributors are written by different teams over time (per the "constitution" framing), none of them can individually erode the boundaries Phases 1–5 established, even with good intentions.

## Determinism principle

**Contributor execution must be deterministic for a given Snapshot ID and contributor version.** Given identical Snapshot ID, contributor version, and input workflow, a contributor must produce the same findings and evidence. This follows directly from Phase 5's manifest-as-immutable-snapshot principle: if the same manifest could yield different results on a re-run, the manifest would stop being a meaningful reproducibility record, and the Explainability success metric (ADR-003, PRD) would be unenforceable in practice even though the domain model enforces it in structure.

Where non-determinism is unavoidable — a probabilistic model, for instance — the contributor's execution metadata (`EvaluationMetadata`, Phase 3) must record enough to explain and reproduce the result as closely as practical: model version, configuration, random seed where applicable. Non-determinism isn't prohibited; being unable to account for it is.

## What Phase 6 deliberately does not answer

- The concrete confidence-aggregation strategy (average, weighted, max-severity-wins, etc.) — an implementation choice within the composition model this phase establishes, not the model itself.
- The literal registration mechanism (a config file, a package-discovery convention, a database-backed registry) — infrastructure detail.
- Which specific contributors beyond Workflow Review actually get built, and when (that's the M26.2–M28 roadmap, a product-sequencing question, not an architectural one).
- Anything about the domain model itself — if implementing this phase turns out to require changing `EngineeringReview`, `Finding`, `Recommendation`, `Manifest`, or `Verdict`, that's a signal to revisit Phase 3, not to quietly patch it here.

## Architecture phase — complete

Phases 1–6 now form the full sequence: architectural invariants (ADR-001 through ADR-005) → bounded context and anti-corruption boundaries → an enforceable domain model → dependency direction and port contracts → persistence principles that don't reshape the domain → an extension framework that admits new contributors without eroding any of the above. No further architecture documents are planned before implementation.

Per the PRD's own implementation-slicing plan, the recommended next step is a minimal vertical slice — one contributor (Workflow Review itself), one workflow type, one immutable review, one persistence path end to end — rather than building out the full contributor ecosystem or every read model before anything runs. That slice is implementation work, not a seventh architecture phase.
