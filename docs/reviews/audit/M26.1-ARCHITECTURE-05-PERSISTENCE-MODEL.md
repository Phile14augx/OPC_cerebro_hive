# M26.1 — Architecture Phase 5: Persistence Model

**Status:** Draft. Builds on Phase 4 (`M26.1-ARCHITECTURE-04-SERVICE-BOUNDARIES.md`). Establishes persistence *principles* first, storage/table specifics second — deliberately, so persistence concerns don't leak back into the domain model finalized in Phase 3. Still not the contributor extension mechanism's internals (Phase 6).

## Principle 1 — persist aggregates, not object graphs

The review persistence port (Phase 4) reconstructs an `EngineeringReview` aggregate on load. It is not obligated to mirror the in-memory object graph one-to-one in storage. This is a persistence boundary, not an ORM-relationship mapping exercise — how `Finding[]`/`Recommendation[]`/`Manifest`/`Verdict` are actually laid out in storage is free to differ from how they're held in memory, as long as reconstruction is faithful.

## Principle 2 — two storage classes, not one

Two classes of data, explicitly separated even if they initially share an underlying database:

**Operational Store** — lightweight, queryable metadata:

```
EngineeringReview
    reviewId
    workflowId
    status
    verdict
    confidence
    manifestHash
    createdAt
    publishedAt
```

Optimized for dashboards, Studio, pipeline lookups, governance queries — the access pattern is "find/filter/list reviews," not "reconstruct full evidentiary detail."

**Immutable Evidence Store** — the heavier, append-only material:

```
Evidence graph
Contributor outputs
Simulation traces
Large semantic changesets
Supporting artifacts
```

Optimized for provenance, audit, reproducibility — the access pattern is "retrieve everything behind a specific finding," which is rarer and can tolerate different (e.g., colder, larger-object-oriented) storage characteristics than the operational store.

This split exists regardless of whether Phase 6 implementation puts both in the same Postgres instance initially — the principle is about access-pattern separation, not necessarily physical separation on day one.

## Principle 3 — the manifest is an immutable snapshot, never recomputed

```
Review
  │
  ▼
Manifest
  │
  ├── Policy Version
  ├── Capability Version
  ├── Contributor Manifest
  ├── Platform Version
  ├── Feature Flags
  └── Snapshot ID
```

A `Manifest` captures the exact execution context a review ran under. It is written once, at review time, and never regenerated to reflect a later state of the platform — doing so would silently invalidate the reproducibility guarantee Phase 3's `Manifest` member exists to provide. Every review is permanently tied to the manifest it was created with, even after the policy version, capability version, or platform version it references has since moved on.

## Principle 4 — versioning by lineage, not mutation

```
Review A          Review B
  (superseded) ──▶ (supersedes A)
```

Re-reviewing a workflow produces a new `EngineeringReview` (new `ReviewId`, new `ReviewVersion`, per Phase 3), linked to its predecessor by lineage, rather than an in-place update of the prior review. `Review A` never changes after `Published` (Phase 3 invariant 4) — this is that same invariant restated as a storage-versioning philosophy rather than left implicit. Consumers that want "the current view" query for the latest in a lineage; consumers that want historical/audit context can walk the lineage backward, and every point in that chain is exactly what it was when published.

## Principle 5 — repository responsibilities are aggregate-scoped only

```
EngineeringReviewRepository
    save()
    load()
    findLatest()
    findByWorkflow()
    findByManifest()
    findByVerdict()
```

The repository deals exclusively with `EngineeringReview` aggregate persistence — it is not the place for contributor-specific or evidence-specific queries. Those belong to the read models (Principle 6) or a dedicated evidence-access service, not to this repository's interface. Keeping the repository's method list this narrow is itself an enforcement mechanism for the aggregate boundary established in Phase 3: if a query needs more than these six shapes, that's a signal it belongs in a read model instead of growing this repository's surface area.

## Principle 6 — read models are separate from the write model

The aggregate is optimized for consistency (Phase 3's invariants must hold on every write). Studio and other consumers are optimized for exploration. These are different concerns and should be modeled as such:

- Review summary
- Review timeline
- Findings by severity
- Policy compliance summary
- Contributor execution summary

Each is a projection derived from published (immutable) reviews, not reconstructed from the live aggregate on every query. Because reviews are immutable once published (Principle 4), these projections don't need complex invalidation logic — a `Published` review's contribution to any read model never needs to change, only be added to.

## Principle 7 — the aggregate owns evidence-reference identity, not evidence storage location

The aggregate maintains stable `EvidenceReference` identities (Phase 3). Where the referenced evidence actually lives — object store, document database, or another mechanism entirely — is an infrastructure decision, deliberately left open per Phase 4's outbound-port framing. The aggregate's contract with the rest of the system is "this reference resolves to this evidence," not "this evidence lives at this specific storage address" — which means the underlying evidence-storage mechanism can change without touching the domain model or any already-published review's meaning.

## Principle 8 — standardize identity types now

Every entity gets a dedicated identity value object rather than a primitive string, extending the `ReviewId` already named in Phase 3 to the rest of the aggregate's members:

- `ReviewId`
- `FindingId`
- `RecommendationId`
- `EvidenceReferenceId`
- `ManifestId`

This is a small addition to Phase 3's value-object list, made explicit here because persistence is where "just use a string" pressure tends to show up first (primary keys, foreign keys, query parameters). Treating these as distinct types from the start avoids, for example, a `FindingId` being accidentally passed where a `RecommendationId` was expected — a class of bug that's cheap to prevent now and progressively more annoying to retrofit later.

## What Phase 5 deliberately does not answer

- Which physical database(s) or storage technology back the Operational Store vs. the Immutable Evidence Store — an implementation decision, not an architectural one, and explicitly allowed to start out colocated per Principle 2.
- The exact schema/columns/document shape for either store.
- How read models are kept up to date (synchronous projection vs. event-driven, per the domain/application/integration event classification from Phase 4).
- The contributor extension mechanism's own persistence needs (a contributor's internal working state, if any) — Phase 6.
