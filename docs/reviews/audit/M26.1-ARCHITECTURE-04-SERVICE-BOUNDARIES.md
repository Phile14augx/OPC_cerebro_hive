# M26.1 — Architecture Phase 4: Service Boundaries

**Status:** Draft. Builds on Phase 3 (`M26.1-ARCHITECTURE-03-DOMAIN-MODEL.md`). Defines dependency direction, inbound/outbound ports, and event classification. Still not concrete persistence/storage decisions (Phase 5) or the contributor extension mechanism's internals (Phase 6).

## Dependency direction

```
Presentation
        │
        ▼
Application
        │
        ▼
Domain
        ▲
Infrastructure
```

Rules, stated explicitly rather than left implicit:

- **The domain depends on nothing.** `EngineeringReview`, `Finding`, `Recommendation`, `Manifest`, `Verdict`, and every value object from Phase 3 are pure — no imports of persistence, transport, or any specific external system's client.
- **The application layer depends only on domain abstractions**, not on concrete infrastructure. It orchestrates: invoked at `publishVersion()` (ADR-004), loads inputs through the ports below, invokes the domain, persists the result, emits events.
- **Infrastructure implements interfaces defined by the application or domain, never the reverse.** A repository implementation depends on a repository interface the domain/application side defines — the arrow points inward, always.
- **Presentation communicates only with the application layer.** Whatever surfaces findings to workflow engineers, platform engineers, and architects (PRD Users) calls application-layer use cases; it never reaches into the domain or infrastructure directly.
- **Contributors are infrastructure components that produce domain objects through stable contracts.** Per ADR-005, a contributor (Workflow Review now; a hypothetical Security/Cost/Compliance/Release Review later) sits on the infrastructure side of this diagram — it's a plug-in that supplies evidence and evaluation behavior through a contract the domain/application layers define, not something the domain depends on directly.

## Inbound ports (use cases invoked by external actors or systems)

- **Initiate a review** — invoked by the application-layer orchestration at `publishVersion()` (ADR-004). This is the only trigger in scope for M26.1 (PRD Trigger); an on-demand/pre-publish variant (PRD Open Question 1) would be a second inbound port reusing the same domain logic, not a change to this one.
- **Query a review / report** — invoked by whatever presentation layer surfaces findings to the PRD's Users. Read-only; does not mutate the aggregate.
- **Re-run a review** — not yet decided as in-scope for M26.1 (not named in the PRD), but worth naming as a plausible future inbound port now so Phase 6 doesn't have to retrofit it. Would produce a new `EngineeringReview` (new `ReviewId`/`ReviewVersion`), not mutate a `Published` one, per the domain model's immutability invariant.

## Outbound ports (dependencies required to execute those use cases)

- **Workflow context port** — supplies the new version's graph and prior version, through the anti-corruption boundary named in Phase 2. Read-only.
- **Capability registry port** — supplies the capability snapshot referenced by `CapabilityReference`. Read-only.
- **Policy evaluation port** — supplies `PolicyEvaluation` outcomes, if an engineering-convention ruleset exists (PRD Open Question 2 / Phase 2's "consumes, does not own" stance). The domain model already accommodates this being unused; the port exists so a future implementation can populate it without a model change, consistent with the Phase 3 rationale for `PolicyEvaluation` as a value object.
- **Review persistence port** — saves/loads `EngineeringReview` aggregates. Interface only at this phase; concrete storage strategy is Phase 5.
- **Evidence-reference persistence port** — plausibly the same port as above (an aggregate and its `EvidenceReference`s persisted together) or a separate one if `EvidenceReference` volume warrants different storage characteristics. Not decided here — flagged for Phase 5.
- **Event publication port** — publishes whatever events the aggregate emits (below). Whether this is the existing Audit Logger/Outbox Publisher (already invoked by `publishVersion()`, per Phase 1) or a dedicated port is still the open question carried since Phase 1 — this phase only establishes that *a* port exists here, not which concrete mechanism backs it.

## Event classification

Three distinct categories, kept separate so operational concerns don't leak into the domain model:

- **Domain events** — immutable facts emitted by the aggregate itself. The clear candidate: a review reaching `Published`. Emitted by the domain, about the domain, with no knowledge of who consumes them.
- **Application events** — orchestration milestones useful for workflows and observability, but not facts about the aggregate's own state machine. Examples: a review being initiated (as opposed to completed), a contributor timing out, an outbound port failing. These originate in the application layer, not the domain.
- **Integration events** — externally consumable contracts other bounded contexts or services subscribe to. A `WorkflowReviewPublished`-shaped integration event, distinct from the internal domain event, is the plausible candidate — deliberately not the same object as the domain event, so this bounded context's internal representation can change without breaking external subscribers, and so external contracts can be versioned independently of the domain model.

This three-way split is itself a boundary worth protecting: a domain event should never be published directly as an integration event without an explicit translation step, for the same anti-corruption reasons Phase 2 named for inbound dependencies.

## What Phase 4 deliberately does not answer

- Concrete storage/schema for the review persistence port — Phase 5 (Persistence Model).
- The literal shape of the contributor contract (registration, ordering, composition, failure isolation, per ADR-005) — Phase 6 (Extension Framework).
- Which existing infrastructure (Audit Logger/Outbox vs. dedicated) backs the event-publication port — still open, carried forward again rather than decided prematurely.
- Wire formats, HTTP/RPC shapes, or any transport-level detail for the inbound ports — those are implementation, not boundary, decisions.
