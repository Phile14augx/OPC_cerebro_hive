# M26.2 / M26.3 — Discovery Notes (Draft)

**Status:** Discovery only. Not a PRD, not an ADR, not an implementation commitment — deferred until M26.1 clears operational verification (`audit/M26.1-BASELINE.md`).

**On how to read this document**: every item below is one of four things, and the heading tells you which:
- **Known** — an established fact, verified against the repository or explicitly confirmed by you.
- **Assumptions** — a working default (often an architectural recommendation) that hasn't been confirmed as your actual intent. Treated as provisional, not decided.
- **Open Questions** — genuinely unresolved; needs your answer before it can move to Known.
- **Deferred Decisions** — acknowledged as a real future decision, deliberately not being made now.

Everything under "Assumptions" in this pass is a recommendation, not a fact about your users or priorities — labeled that way explicitly so it can't be quietly read back later as something you confirmed.

## 1. API Consumers

**Known**
- Studio (the existing Next.js frontend) is the platform's existing UI surface and the most obvious first consumer of any Engineering Review API.

**Assumptions**
- *Recommendation, not confirmed*: optimize the first API iteration for Studio as the primary consumer —
  ```
  Engineering Review Domain → Operational API → Studio
  ```
  CLI (CI/CD integration), an automation/API client, and an IDE extension are plausible secondary consumers to design *for* (i.e. don't paint the API into a corner) but not to *optimize for* in the first release.

**Open Questions**
- Do CLI or automation-client consumers actually exist as a near-term need, or are they purely speculative right now?
- Is the API internal-only, partner-facing, or public?
- Synchronous or asynchronous access — does anything need to trigger a review and then poll/wait, or is everything read-after-the-fact?

**Deferred Decisions**
- API versioning strategy for external consumers.

## 2. Primary Studio Persona

**Known**
- (none yet — no persona has been confirmed against real usage)

**Assumptions**
- *Recommendation, not confirmed*: design for a single primary persona first — the **Engineering Tech Lead / Reviewer** — reasoning being that this role bridges reviewing workflow changes, understanding findings, deciding whether to proceed, and communicating issues back to the workflow author. Individual workflow engineers, security engineers, compliance officers, and engineering leadership are treated as secondary personas to layer on later, not to design the first pass around.

**Open Questions**
- Does the Tech Lead/Reviewer framing actually match who would use this day to day, or is the primary user actually the workflow author themselves (self-service, before anyone else looks at it)?
- Do Security/Compliance personas matter for M26.3 at all before their corresponding contributors (M26.2+/M27 per the Phase 6 roadmap sketch) exist?

**Deferred Decisions**
- Full persona-specific view design for anyone beyond the primary persona.

## 3. Performance Targets

**Known**
- (none — no SLA has been set)

**Assumptions**
- *Recommendation, not confirmed*: qualitative targets rather than invented numbers, until real usage exists to measure against:

  | Interaction | Target |
  |---|---|
  | Review list | Feels instantaneous |
  | Open review | Interactive |
  | Expand evidence | Progressive loading |
  | Comparison view | Responsive |
  | Executive analytics | May tolerate higher latency |

**Open Questions**
- Are there any real constraints already known (expected review volume, expected concurrent users, expected findings/evidence count per review) that should turn any of the above into an actual number?
- Retention period for operational read models (Phase 5 §2) — how long should a review stay queryable before archival matters?

**Deferred Decisions**
- Precise numeric SLAs — intentionally not set until real usage data exists.

## 4. Review Navigation

**Known**
- (none yet)

**Assumptions**
- *Recommendation, not confirmed*: a canonical journey with recommendations placed deliberately *after* evidence —
  ```
  Review → Summary → Findings → Evidence → Recommendations → Raw provenance
  ```
  Reasoning: this ordering reinforces the domain's own invariant (ADR-003, Phase 3) that recommendations are consequences of evidence, not the other way around — the navigation order and the domain's dependency direction should agree, not just coincidentally match.

**Open Questions**
- Does this match how someone would actually want to drill into a review, or would findings-first (skipping straight past the summary) be more natural for daily use?
- How often is comparing two reviews (current vs. prior) actually needed, and should that be a first-class navigation path rather than something reached indirectly?

**Deferred Decisions**
- Whether a stale/superseded review should surface as "outdated" immediately or only on request.

## 5. Progressive Disclosure

**Known**
- (none yet)

**Assumptions**
- *Recommendation, not confirmed*: a five-level disclosure hierarchy, framed by the principle "every screen should answer the user's immediate question before exposing implementation detail":
  ```
  Level 1 — Overall verdict, severity, summary
  Level 2 — Findings
  Level 3 — Supporting evidence
  Level 4 — Contributor diagnostics
  Level 5 — Raw snapshot metadata
  ```
  Expectation: most users never need Levels 4–5, but provenance stays reachable when needed (directly serving the Explainability success metric from the M26.1 PRD).

**Open Questions**
- What's genuinely "on demand only" vs. what should load eagerly, once real evidence volume per review is known?

**Deferred Decisions**
- Exact eager-vs-lazy loading boundaries — depends on real evidence volume, not yet known.

## 6. Unit of Review — new question, not yet in any prior draft

**Known**
- The domain model (Phase 3) is built around one `EngineeringReview` per `(workflowId, reviewVersion)` — i.e. the unit of review as currently implemented is **one workflow version**.

**Open Questions**
- Is "one workflow" the right unit going forward, or should the platform eventually support reviewing a pull request, a deployment, a policy evaluation, or a release candidate as its own unit? This affects URLs, navigation, search, comparisons, analytics, and permissions — flagged as foundational precisely because it's expensive to change later.

**Deferred Decisions**
- Whether the unit of review ever expands beyond "one workflow version" — not needed for M26.1/Slice 1–2, which only ever modeled the workflow-version case (per ADR-004, this was scoped to workflow publication specifically, not CI/CD releases or any other unit).

## 7. Review "Done" Lifecycle — new question, not yet in any prior draft

**Known**
- The domain model's lifecycle (Phase 3) is: `Draft → EvidenceCollected → EvaluationCompleted → RecommendationsGenerated → Published`, and `Published` is terminal and immutable (invariant 4) — there is no state after `Published` in the current implementation.

**Open Questions**
- Does "done" for a *product* purpose end at `Published`, or is there a further human-facing state needed — e.g. `Human Reviewed` or `Archived` — layered on top of (not replacing) the domain's own immutable `Published` state?
- If such a state exists, is it tracked as review metadata (an operational-store field, per Phase 5 §2) rather than a domain lifecycle change, so `EngineeringReviewReport`'s own invariants aren't reopened for a UI/product concern?

**Deferred Decisions**
- Whether any post-publish human-facing status gets added at all — not needed until Studio's actual review workflow is defined.

## Consolidated Open Questions (for you to answer directly, whenever convenient)

1. Are CLI/automation-client consumers real near-term needs, or speculative?
2. Does "Tech Lead/Reviewer" match the actual primary daily user, or is it the workflow author?
3. Any real volume/concurrency numbers that should replace the qualitative performance targets?
4. Is comparing two reviews frequent enough to be first-class navigation?

## Candidate future ADR (not authored — flagged for M26.2's ADR pass)

Arising from the "done" lifecycle discussion (§7): if a human-facing operational workflow (e.g. `Published → Assigned → Reviewed → Disposition Recorded → Closed`) is layered on top of the domain's immutable lifecycle, the boundary between the two should be a named architectural decision, not an implicit convention. Candidate statement for a future ADR, once M26.2 is actually being scoped:

> Operational workflow state must never mutate domain lifecycle state. `EngineeringReviewReport`'s own lifecycle (`Draft → ... → Published`) and invariants (Phase 3) remain exactly as implemented in the M26.1 baseline; any human-facing status beyond `Published` is tracked as separate operational-store metadata (Phase 5 §2), never as a new domain state or a reopening of the `Published` aggregate.

Not written as an ADR now — doing so would be authoring M26.2 architecture ahead of its PRD, which is exactly the sequencing this document is deferring. Recorded here so it isn't lost between now and whenever that ADR pass happens.
