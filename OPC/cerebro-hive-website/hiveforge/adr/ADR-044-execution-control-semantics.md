# ADR-044: Execution Control Semantics — Authorization, Cancellation, Timeout (Phase 9f-1)

**Status:** Proposed (Phase 9f-1 of `09-EXECUTION-LIFECYCLE-RUNTIME.md`; builds on `ADR-039` through `ADR-043`)

## Context

Every prior Phase 9 ADR named the same three concerns and explicitly deferred them to "Phase 9f": `ADR-041` ("this class never decides who is authorized... cancellation... nothing here drives them... timeout detection... out of this class's scope"). Before building 9f, its unusually large proposed scope (nine distinct areas: authorization, cancellation, timeout, retry, idempotency, duplicate handling, leases/ownership, failure classification, transition invariants) was raised explicitly, per the discipline every sub-phase in this masterplan has used. Per direction, 9f is split in two:

- **9f-1 (this ADR): Execution Control** — authorization, cancellation, timeout, and the transition invariants those introduce. Answers "can this Execution legally move from state A to state B, and who is allowed to make it?"
- **9f-2 (not yet started): Reliability & Ownership** — retry semantics, idempotency, duplicate-request handling, leases/ownership, failure classification. Answers "what happens when things go wrong or happen more than once?"

Also per direction, 9f-1 stays standalone in the same sense 9a-9e did: it defines contracts, semantics, and deterministic test doubles, not production infrastructure. The only exception named: reference implementations used solely for verification (e.g. a deterministic clock), which are test fixtures, not production code, and are kept in test files rather than exported from the package.

## Decision

**1. Authorization is a real, injected `ExecutionAuthorizationPolicy`, reusing existing infrastructure rather than inventing a parallel one.** `ExecutionAuthorizationPolicy.ts` defines `ExecutionAuthorizationPolicy` as `IPermissionPolicy<ExecutionAuthorizationContext, Execution>` — directly reusing `packages/domain/src/policies/Decision.ts`'s existing `Decision`/`IPermissionPolicy` shapes (same package, not a cross-bounded-context import; `PolicyEngine.ts` itself is deliberately NOT imported, since it couples to `@cerebro/database`'s `RequestContext`, a dependency this aggregate has stayed off of throughout Phase 9). `ExecutionOrchestrator` gains an optional constructor `authorizationPolicy`, defaulting to a real, explicit `AllowAllExecutionAuthorizationPolicy` — permissive by design, matching every existing caller's unchanged behavior, and a visible, named default rather than a silent absence of a check (learned directly from this same session's earlier mandatory-version-concurrency reconciliation, where an *optional*, silently-skippable check was judged a real gap). Every transition `ExecutionOrchestrator` drives — including `cancel`/`resume` actions, not only ordinary lifecycle steps — now passes through this policy; a denied `Decision` raises the pre-existing `AuthorizationError` (`DomainError.ts` already had this error type, unused until now — another instance of reuse before invention).

**2. Cancellation is a real, single-process, cooperative primitive (`ExecutionCancellation.ts`), explicitly not a distributed preemption mechanism.** `ExecutionCancellationTokenSource`/`ExecutionCancellationSignal` mirror the standard `AbortController`/`AbortSignal` split: the orchestrator alone holds the writable token; `ExecutionProviderPort.execute()` gains an optional, read-only `cancellationSignal` a real provider MAY observe cooperatively (ignoring it is still correct — the orchestrator honors cancellation once the provider call returns regardless). Two new orchestrator methods:
   - `requestCancellation(execution, opts)` — authorization-gated. If the Execution is CREATED/VALIDATING/QUEUED (no CANCELLING intermediate exists in `ExecutionTransitions.ts`'s graph for these — no real work has started), it only records the token; the in-flight `run()`/`retry()` step loop's own pre-RUNNING check (`checkAndFinalizeIfCancelled()`) finalizes straight to CANCELLED before its next step. If RUNNING or WAITING, it transitions immediately to CANCELLING.
   - `acknowledgeCancellation(execution, opts)` — the only way out of CANCELLING; moves to CANCELLED (`opts.succeeded` true, default) or FAILED (cleanup itself did not complete cleanly — a real, legal edge the transition graph already had). Throws if the Execution is not currently CANCELLING.

   **Once CANCELLING has been entered, cancellation is committed** — a provider that still reports `'completed'` after cancellation was requested does not retroactively override it (the transition graph has no CANCELLING → COMPLETED edge to race against; this was found and fixed via a real failing test during verification, not designed correctly on the first attempt).

**3. Timeout is enforced via an injected `Clock` (`Clock.ts`) and an optional `RunExecutionInput.timeoutMs`, checked only around the provider invocation and on `resume()`.** `Clock`/`SystemClock` (real, production default) exist so timeout is deterministically testable — a test drives a `DeterministicClock` (kept as a test fixture in `ExecutionControlSemantics.test.ts`, not exported production code, per the "reference implementations for verification only" scoping) forward past a deadline rather than sleeping in real time. Deliberately NOT enforced during CREATED/VALIDATING/QUEUED: `ExecutionTransitions.ts`'s graph only allows `TIMED_OUT` from RUNNING or WAITING, so admission/queueing latency is treated as a different concern from "the work itself took too long," rather than silently violating the already-locked transition graph to force a new edge. **Timeout takes precedence over whatever the provider reports** if the deadline has already passed, including an outright `'completed'` result arriving too late — this directly answers the "when does timeout supersede retry [outcome]?" question raised when 9f's scope was first proposed.

**4. Transition invariants are enforced at the orchestrator layer, not added to `Execution.transitionTo()` itself.** No change was made to `Execution.ts`'s own structural invariants (the CANCELLING-requires-a-reason rule was considered and explicitly rejected — `ExecutionEventContract.test.ts` already has a test titled "ExecutionWaitingEvent and ExecutionCancellingEvent carry an optional reason," part of the event contract locked down and praised as a stable boundary in an earlier phase; reopening it for 9f-1 was judged not worth disturbing a settled, reviewed contract for a marginal invariant). Instead, the new invariants this phase introduces are orchestration-level: every transition is authorization-gated; `acknowledgeCancellation()` may only be called from CANCELLING; a pending cancellation, once committed, cannot be overridden by a provider's outcome; a passed timeout deadline always supersedes a provider's outcome. This keeps `Execution`'s own scope exactly as `ADR-039`/`ADR-041` already drew it: the aggregate enforces structural well-formedness and transition legality; who may act and when work has run too long are orchestration concerns layered on top.

## Consequences

- `ExecutionOrchestrator`'s constructor gained an additive 4th, optional parameter (`{ authorizationPolicy?, clock? }`) — every existing call site (9c/9d/9e's own tests) continues to work unchanged, since both default to real, permissive/production behavior.
- `ExecutionProviderPort.execute()` gained an additive, optional second parameter — existing fakes/providers that ignore it remain valid implementations by TypeScript's structural typing (fewer parameters than the interface declares is assignable).
- Distributed/cross-process cancellation propagation (a worker on another node actually stopping), a live recurring timeout-sweep process, and a real authorization backend are explicitly out of scope — 9f-1 defines the contracts and a single-process reference behavior; wiring any of it into a live runtime is Phase 9g's job, and a real backing `IPermissionPolicy` implementation (e.g. via `HierarchicalPolicyEngine` or similar) remains a future integration, not built here.
- Retry semantics, idempotency, duplicate-request handling, leases/ownership, and failure classification remain entirely unaddressed by this ADR — that is 9f-2's explicit scope, not silently folded in or silently dropped.

## Implementation status — Complete for 9f-1's own (standalone) scope; no live authorization backend, scheduler, or distributed cancellation touched

New files: `Clock.ts` (`Clock`/`SystemClock`), `ExecutionCancellation.ts` (`ExecutionCancellationSignal`/`ExecutionCancellationTokenSource`), `ExecutionAuthorizationPolicy.ts` (`ExecutionAuthorizationPolicy`/`ExecutionAuthorizationContext`/`AllowAllExecutionAuthorizationPolicy`) — all exported from `packages/domain`'s root `index.ts`. `ExecutionOrchestrator.ts` extended: `requestCancellation()`, `acknowledgeCancellation()`, per-transition authorization checks, timeout-deadline checks in `run()`/`resume()`/`invokeProviderAndFinalize()`. `ExecutionProviderPort.execute()`'s signature extended additively. Verified, not assumed:

- Real `tsc --strict` typecheck (scratch-toolchain pattern) — clean across the whole `execution/` package, including the three new files and the new test file.
- Real `vitest` run — **116/116 tests passing** across the whole `execution/` package (15 new, in `ExecutionControlSemantics.test.ts`): permissive-default behavior, `AuthorizationError` rejection with the denying `Decision`'s own reason, per-transition context (actor/action/target status) reaching the policy, cancel-action-specific denial, pre-RUNNING cancellation short-circuit (provider never invoked), cooperative RUNNING-cancellation via `requestCancellation()` followed by `acknowledgeCancellation()` to both CANCELLED and FAILED outcomes, the CANCELLING-precondition-violation error, terminal-Execution cancellation no-op, the cancellation-commitment behavior found and corrected via a real failing test during this same verification pass, the read-only `cancellationSignal` actually flipping observably mid-provider-call, and four timeout scenarios (no-deadline unaffected, deadline-passed-during-provider overriding a `'completed'` result, deadline-already-passed-before-RUNNING skipping the provider entirely, and `resume()` timing out directly from WAITING without re-entering RUNNING). One pre-existing 9c test (`ExecutionOrchestrator.test.ts`) was updated for the additive `execute()` signature change (asserting the call now includes the `cancellationSignal` argument), not otherwise altered.
- Scratch verification artifacts removed after the run.
- Not yet done, and not claimed as done: 9f-2 (retry/idempotency/duplicate-detection/leases/failure-classification); a real `IPermissionPolicy` backend for `ExecutionAuthorizationPolicy`; any live scheduler driving timeout sweeps or resumption; distributed cancellation propagation across processes; Phase 9g's live runtime wiring of any of Phase 9's deliverables to date.
