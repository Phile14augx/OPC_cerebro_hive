# ADR-051: End-to-End Verification Strategy (Phase 9g-6)

**Status:** Proposed (Phase 9g-6 of `09-EXECUTION-LIFECYCLE-RUNTIME.md`; builds on `ADR-039` through `ADR-050`)

## Context

9g-1 through 9g-5 each built and verified one node of the execution pipeline in isolation (runtime providers, scheduler, workers, event delivery, observability), following a common "adapters/contracts only, honestly unverified against live infrastructure" discipline once the phase's scope touched anything infra-shaped. What none of those sub-phases did — because each was scoped to its own node — was exercise the whole pipeline wired together: a command reaching `ExecutionOrchestrator`, driving the `Execution` aggregate through real transitions, producing domain events, durably recording them via the transactional outbox, relaying them to a consumer, and (in parallel) delivering them synchronously to an in-process subscriber, all while observability signals are recorded throughout — and doing so across the full scenario matrix a production execution engine needs to handle correctly (retries, cancellation at every phase, timeouts, duplicate commands, crash recovery). Per explicit direction, matching the discipline that scoped 9g-5: verify everything a deterministic, in-process environment can genuinely prove, and explicitly defer anything that requires external infrastructure this sandbox does not have (a live Postgres/NATS instance, multiple real processes, a container orchestrator, a chaos-testing harness).

## Decision

**1. One end-to-end test suite (`ExecutionEndToEnd.test.ts`) builds a single `Pipeline` harness composing every real 9a-9g-5 component** — `InMemoryExecutionRepository`, `TransactionalOutboxExecutionEventSink` + `InMemoryExecutionEventOutboxStore`, `ExecutionEventRelay` + a recording `ExecutionOutboxEventPublisher` (standing in for a real consumer, same pattern `OutboxRelayExecutionEventSink.test.ts` already established), an `InMemoryEventBus` subscriber (the in-process delivery path 9g-4 demonstrated needs no adapter), and `DefaultExecutionTelemetry` backed by the three 9g-5 in-memory adapters — via a test-local `FanOutExecutionEventSink` that publishes every event to both the outbox and the event bus. This composite sink is deliberately NOT added to `packages/domain`'s public exports: production callers choose exactly one delivery mechanism (or their own composition), and this specific pairing exists only to prove both paths work correctly off the same event stream within one test run.

**2. The scenario matrix in the original 9g-6 proposal is exercised as a matrix of real tests, not asserted by inspection** — happy path, provider failure, retry success, retry exhaustion, cancellation at each of its three meaningfully distinct points (before/during/after execution), timeout, duplicate-command idempotent replay, event ordering, and simulated crash recovery (both at the outbox/relay layer and via `ExecutionReplay`'s transitionHistory-based reconstruction). "Validation failure" is the one scenario exercised directly against the `Execution` aggregate rather than through the orchestrator — `ExecutionOrchestrator.driveNewExecution()` has no real validation logic of its own to fail yet (it always proceeds VALIDATING -> QUEUED unconditionally), so this test demonstrates the aggregate's own transition graph correctly supports a validation-failure outcome, honestly disclosed as a substitute for an orchestrator-level trigger that does not exist. See `09g6-EXECUTION-E2E-VERIFICATION.md` for the full scenario-to-test mapping (the "failure matrix").

**3. State machine and outbox properties (legal/illegal transitions, version increments, optimistic concurrency, persistence/relay/duplicate-suppression/ordering/crash-recovery) are asserted directly, not inferred from scenario outcomes** — e.g. a dedicated test attempts a stale `expectedVersion` save and asserts `ConcurrencyError`, rather than relying on a scenario test to incidentally exercise it. This keeps each property's pass/fail independently diagnosable.

**4. "Crash recovery" is simulated by discarding in-memory object references, not by starting or stopping a real process.** Two variants are exercised: (a) a fresh `ExecutionEventRelay`/publisher pair constructed only from the surviving `ExecutionEventOutboxStore`, confirming the relay resumes and delivers exactly the still-pending entries exactly once; (b) `ExecutionReplay.replayExecution()` reconstructing an Execution's full state purely from `ExecutionRepository.loadTransitions()` output, with no live event store or snapshot involved — the direct, executable proof of `ADR-040`'s own claim that `transitionHistory` is sufficient for deterministic replay. Neither variant proves anything about a REAL process crash (unflushed OS buffers, partial writes, a real database's own crash-recovery semantics) — that would require a real process and a real datastore, both absent here.

**5. Property-based/random-command-sequence testing (the original proposal's optional 7th category) was considered and explicitly not built.** The fixed scenario matrix already exercises every legal-transition edge in `ExecutionTransitions.ts`'s graph, and any randomly-generated command sequence would, by construction, only ever produce sequences the state-machine tests already classify as legal-or-rejected — a real cost/benefit judgment, not an omission glossed over.

## Consequences — Implemented / Verified / Deferred

**Implemented:**
- `ExecutionEndToEnd.test.ts` — 21 tests spanning full-pipeline wiring, the complete lifecycle scenario matrix, state machine verification, outbox verification, deterministic replay, and cross-pipeline observability verification.
- `09g6-EXECUTION-E2E-VERIFICATION.md` — the lifecycle verification record, failure matrix, and recovery matrix, mapping every scenario to its test and its verified outcome.

**Verified (in this sandbox):**
- Real `tsc --strict` typecheck — clean across the whole `execution/` package, including the new end-to-end suite.
- Real `vitest` run — **188/188 tests passing** across the whole `execution/` package (21 new). Every execution lifecycle path named in the original 9g-6 scope (happy path, validation failure, provider failure, retry success, retry exhaustion, cancellation before/during/after execution, timeout, duplicate delivery/idempotent replay, event ordering, simulated crash recovery) is exercised by a real, passing test — none by mocked-and-assumed behavior. Correlation IDs were confirmed, by direct field comparison (not inspection), to propagate from the aggregate through every telemetry signal (spans, metrics, structured logs) across a full pipeline run.
- No mocked behavior is presented as verified functionality: every component in the pipeline (repository, outbox, relay, event bus, telemetry) is the real, standalone implementation built and separately unit-tested in its originating sub-phase — the only test-local additions are a recording `ExecutionOutboxEventPublisher` (a real, minimal implementation of the real contract, same pattern as every prior phase's "Recording"-prefixed fixtures) and the `FanOutExecutionEventSink` composition described in decision 1.

**Deferred (explicitly, not glossed over — all require external infrastructure not present in this sandbox):**
- Live PostgreSQL — no real database-backed `ExecutionRepository`/`ExecutionEventOutboxStore` was exercised; only the in-memory reference implementations.
- Live NATS JetStream — no real message broker received or delivered anything; the "Consumer" node is a recording in-memory publisher throughout.
- Multi-process orchestration — every test in this suite runs in a single process, single thread, with no real inter-process communication.
- A real OpenTelemetry Collector, Prometheus, or Grafana — observability verification used the same in-memory adapters `ADR-050` built and disclosed as non-production-backend-verified.
- Kubernetes or Docker Compose integration — nothing in this suite starts, stops, or coordinates containers.
- Chaos engineering across distributed nodes, network partitions, or cross-process failover — there is only one process and no network in this suite.
- Horizontal scaling or production performance benchmarks — no load, throughput, or latency-under-scale claim is made or tested anywhere in this phase.

## Acceptance criteria — met, within stated scope

Every execution lifecycle path named in the original 9g-6 proposal is exercised by a real, passing test (§ scenario matrix above). No mocked behavior is presented as verified functionality — every pipeline component is the real, standalone implementation from its originating sub-phase, and every "recording" fixture is a genuine implementation of the real contract it stands in for, not a mock-framework double. Every deferred capability is named explicitly, both here and in `09g6-EXECUTION-E2E-VERIFICATION.md` §6, as requiring external infrastructure this sandbox does not have. The execution engine is shown, by direct, passing tests, to behave correctly from command submission through event delivery, retry, cancellation, timeout, and simulated crash recovery — within the constraints of this in-process environment, and not beyond them.

## Implementation status — Complete for 9g-6's own (standalone, in-process) scope; this is the last sub-phase of the originally-proposed 9g-1 through 9g-6 roadmap

New files: `packages/domain/src/execution/__tests__/ExecutionEndToEnd.test.ts`, `hiveforge/09g6-EXECUTION-E2E-VERIFICATION.md`. No production code was modified or added — 9g-6 is purely a verification pass over the already-built 9a-9g-5 surface, composing existing public APIs rather than changing any of them. Scratch verification artifacts removed after the run. With 9g-6 complete, the entire 9g roadmap (Runtime Providers, Scheduler, Workers, Event Delivery, Observability, End-to-End Verification) is now implemented and honestly verified to the limits of this sandbox — live infrastructure integration (Postgres, NATS, a real OTel/Prometheus/Grafana stack, multi-process/distributed operation) remains explicitly future work, not claimed as done anywhere in Phase 9's documentation.
