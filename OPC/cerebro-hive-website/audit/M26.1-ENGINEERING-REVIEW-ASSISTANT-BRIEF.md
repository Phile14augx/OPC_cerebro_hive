## M25 Workflow-Versioning Verification *(Confirmed by repository inspection)*

Scoped, narrow check of the assumption the Problem statement below relies on. Not a broad audit.

| Claim | Status | Evidence |
|---|---|---|
| A versioned workflow artifact exists | **Confirmed** | `WorkflowVersion` is a real Prisma model (`packages/database/prisma/schema.prisma`): `id`, `workflowId`, `version: Int`, `@@unique([workflowId, version])`, related `nodes`/`edges`. Backed by a real repository (`WorkflowRepository.publishVersion`/`getLatestVersion`) and a real application service (`WorkflowApplicationService.publishVersion`) with policy check, validation, a transactional unit of work, audit logging, and an outbox-published `WorkflowPublishedEvent`. This is a genuinely well-built feature, not a stub. |
| Immutability is enforced by the data model | **Partial** | No DB-level enforcement (no revoked `UPDATE` grant, no trigger/constraint preventing mutation of an existing row). Immutability holds by API-surface design instead: `WorkflowRepository` exposes only `create`-shaped methods (`createWorkflow` creates version 1, `publishVersion` always inserts a new row with `nextVersion = latest + 1`) — there is no `updateVersion` method anywhere in the repository for anything to call. That's a real but softer guarantee than a schema-level constraint; a future repository method or a raw query could still violate it. |
| What is versioned | **Confirmed, narrowly scoped** | Only the workflow graph structure: `WorkflowNode` (name, type, JSON `config`) and `WorkflowEdge` (source/target node references, optional `condition`). Not diagnostics, not policy state, not compilation output — those aren't part of `WorkflowVersion` at all. |
| Versioned release artifacts | **N/A — term conflates two unrelated things** | See below. |
| Release pipeline consumes versions | **Not present** | Checked `release-train.yml` directly (already read in full for Stream C): its only "workflow" references are GitHub Actions' own generic vocabulary (`workflow_dispatch`, `.github/workflows/argocd-sync-retry.yml`) — zero relationship to the product's `WorkflowVersion` entity. The CI/CD "release pipeline" (`release-train.yml` → ArgoCD → canary) deploys application code/infrastructure; it has no code path that reads or reacts to a tenant's workflow being published. |
| Compilation cache versioning | **Not present** | No evidence found of a separate compiled/cached representation tied to a `WorkflowVersion`; only the raw graph (nodes/edges) is persisted. |

**Correction this requires to the Problem statement below**: "workflow versioning" and "the release pipeline" are two real but *entirely separate* systems in this repository, not one flowing into the other as the original framing implied. `WorkflowVersion` publishing is an in-product, per-tenant action gated by `WorkflowApplicationService`'s own `policyEngine.evaluate('CanPublishWorkflow', context, ...)` call — a different, already-existing policy checkpoint from the CI-level `pnpm policy:check` stub in `release-train.yml` that the Integration Points section previously pointed to. If M26.1 is meant to review workflow publishes specifically, **`WorkflowApplicationService.publishVersion()`'s existing policy-check step is the grounded integration point**, not `release-train.yml`. If M26.1 is meant to review *application/infrastructure* releases (the CI/CD sense), then `release-train.yml` remains the right integration point, but it has nothing to do with workflow versioning — the Problem statement should pick one meaning of "release" and be explicit about which.

## Problem *(Proposed — revised after the verification above)*

Two separate things are both real in this repository, and this brief needs to be explicit about which one it's addressing:

1. **CI/CD releases** (`release-train.yml` → ArgoCD → canary rollout) assess whether a *code/infrastructure* change is technically deployable: does it compile, are required capabilities and secrets present, does the Helm render succeed, does the canary rollout stay healthy.
2. **Workflow publishing** (`WorkflowApplicationService.publishVersion()`, confirmed real above) is a separate, in-product, per-tenant action — a user publishing a new version of their own automation/agent workflow — already gated by its own policy check (`policyEngine.evaluate('CanPublishWorkflow', ...)`), independent of anything in `release-train.yml`.

Neither currently answers a further class of question:

They do not answer a different class of question:

- Does this change introduce unnecessary architectural complexity?
- Does it duplicate a capability that already exists elsewhere in the platform? (This audit found several real instances of exactly this — the two Helm template generations, the two PolicyEngine-shaped implementations found during M25.4A, `apps/platform-api` vs. `apps/studio/platform` both calling themselves "the platform API.")
- Is there a simpler or safer implementation pattern available?
- Does the change violate an engineering convention or policy the team has established?
- What's the actual evidence behind a reviewer's "looks fine" or "this is risky"?

The gap is not deployment readiness — it's **engineering judgment**, applied consistently and with a documented evidence trail, before a change reaches the point where a human has to approve it.

## Goal *(Proposed)*

Provide evidence-backed engineering reviews before a workflow/change enters the release approval process. **The assistant recommends; humans approve.** It should surface findings with citations to the actual code/config it read, the same way this audit did — not a bare risk score with no way to check its work.

## Users *(Proposed)*

Not yet confirmed with you — proposed based on who `release-train.yml` already puts in the loop:

- **Release engineers** — the ones opening/reviewing the auto-generated release PR today; the assistant's findings would most naturally attach there.
- **Tech leads / architects** — the audience for architectural-drift-style findings (duplication, complexity, convention violations) rather than line-level code review.
- Whether **security reviewers** are a distinct audience, or folded into "tech lead," is an open question — see below.

## Decision Point *(Proposed)*

Most natural fit, grounded in what already exists: **after `test-suite` and the existing `policy gate` step, before `deploy-staging`**, in `release-train.yml`. That workflow already has a stub for exactly this kind of gate:

```yaml
- name: Policy gate
  run: |
    echo "Policy gate: checking Helm manifests"
    pnpm policy:check || true
```

This is a real, existing integration point that's currently a soft no-op (`|| true` — same pattern this audit just fixed for the AgentOS health check). Whether the Engineering Review Assistant *replaces* this step, extends it, or runs as a separate parallel stage is an open question, not decided here.

## Inputs *(Grounded in existing platform where applicable)*

Grounded — these already exist and could plausibly feed a reviewer:
- The diff/PR content itself (`release-train.yml` already checks out `RELEASE_BRANCH` and has full git history via `fetch-depth: 0`).
- Rendered Helm manifests (a `helm template` render — the same artifact this audit's own CI recommendation in `INFRA-RECONCILIATION-PLAN.md` §5 proposes generating for duplicate-identity/unconsumed-value checks).
- The runtime capability registry (`RuntimeRegistry`/`CapabilityDescriptor`, built and tested earlier this session in `apps/platform-api`) — a real, structured source of "what capabilities exist" that a duplication-detection check could query against.
- Existing policy engines — there are at least four real, independent implementations found during M25.4A (`packages/policy`, `packages/policy-core`, `apps/studio/platform`'s kernel `PolicyEngine`, plus the domain-package one wired into `apps/platform-api`). Any of these could plausibly supply the "organizational convention" ruleset, though none is currently used for this purpose.

Proposed, not yet grounded:
- A structured "workflow graph" / version-metadata input, as referenced in the Problem statement's framing of prior M25 work — this audit did not verify that immutable versioned workflow artifacts exist in the form implied; flagging this as an assumption carried into this brief rather than a confirmed fact.
- Diagnostics/observability data as a review input (e.g., from `apps/studio/platform`'s `ObservatoryService` or the K8s side's Grafana/Prometheus stack) — plausible, not scoped.

## Outputs *(Proposed)*

- A structured risk/readiness assessment, not a single score — this audit's own documents (evidence → conclusion → confidence level, revised when wrong) are the intended model, not a black-box number.
- Findings should cite what was read (file, line range, or rendered artifact) the way this audit's documents do, so a human reviewer can verify rather than trust blindly.
- A recommendation (approve / flag / block), explicitly advisory — final approval stays human, per the Goal statement above.

## Integration Points *(Grounded in existing release pipeline architecture)*

- `release-train.yml`'s `policy-gate`-adjacent step (the `pnpm policy:check || true` stub) is the most concrete existing hook.
- `argocd-sync-retry.yml`'s incident-issue-creation pattern (opens a GitHub issue with structured findings on failure) is a reusable pattern for how this assistant could surface findings without inventing a new UI.
- Whether it should also gate the VPS path (`ssh-deploy.yml`, which currently has *no* gating at all before deploying to `cerebropchive.org`) is an open question — that pipeline has no test/policy stage today, so adding one there would be a bigger scope increase than extending the K8s release train.

## Entry / Exit Criteria *(Proposed)*

Not yet defined. Needs your input on: what triggers a review (every release-train run? only flagged file paths? on-demand?), and what constitutes a passing vs. blocking exit state.

## Non-goals *(Proposed)*

- Not a replacement for the existing test suite, policy gate, or staging smoke tests — additive, not a substitute.
- Not an autonomous approval mechanism — explicitly recommends, does not approve (per Goal).
- Not scoped (yet) to cover the VPS deployment path, which has no equivalent gated pipeline today.

## Success Metrics *(Proposed)*

Not yet defined — needs your input. Candidate directions only: reduction in post-release architectural-drift findings (the kind this audit surfaced after the fact), reviewer time saved, or a measured rate of findings a human reviewer confirms vs. dismisses (a precision signal, to avoid the tool becoming noise that gets ignored).

## Open Questions *(Explicitly unresolved)*

1. Scope: code/architecture review, deployment/infra review, or both unified (this was the first clarifying question asked earlier and never got answered — still open).
2. Integration point: extend the existing `policy:check` stub, add a new parallel stage, or build as an on-demand standalone service first and wire into CI later.
3. Are security reviewers a distinct user/audience from tech leads, with different finding types?
4. Should this ever gate the VPS/`cerebropchive.org` path, which has no equivalent review stage today?
5. Which of the four existing PolicyEngine-shaped implementations (if any) should supply the "organizational convention" ruleset, or does this need its own?
6. Is the "immutable, versioned workflow artifacts" premise in the Problem statement something you can confirm exists in the form assumed, or does that need its own verification pass before this brief's Inputs section is fully grounded?
