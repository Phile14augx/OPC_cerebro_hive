# M26.1 — Implementation Roadmap

**Status:** Architecture complete (see `M26.1-INDEX.md` for the full document set). This roadmap sequences implementation into vertical slices, per the PRD's original slicing intent. Each slice below is tagged with the architecture sections it must conform to — the traceability convention this roadmap adopts and expects every implementation PR to follow.

## Traceability convention (normative from here forward)

Every PR implementing part of M26.1 should declare what it implements and what architecture it was reviewed against, e.g.:

```
Implements:
- ADR-005
- Phase 3 §Aggregate Lifecycle
- Phase 4 §Outbound Ports

Architecture References
✓ ADR-004
✓ Phase 5 §Repository Rules
✓ Phase 6 §Contributor Contract
```

This isn't bureaucracy for its own sake — it's what lets a reviewer verify conformance to intended design, not just that the code works, and it's what will keep future contributors (per ADR-005/Phase 6) from silently drifting away from the invariants documented across `ADR-001` through `ADR-005` and Phases 1–6.

## Slice 1 — Skeleton

- `EngineeringReview` aggregate (report shape only — no contributors yet).
- Value objects: `ReviewId`, `FindingId`, `RecommendationId`, `EvidenceReferenceId`, `ManifestId`, and the rest from Phase 3/5.
- Aggregate lifecycle (`Draft → EvidenceCollected → EvaluationCompleted → RecommendationsGenerated → Published`), enforced internally per Phase 3.
- Repository interface + an in-memory implementation (no real persistence yet — that's Slice 3).
- Basic tests validating the lifecycle invariants (§ Phase 3 invariants 1–12) cannot be violated through normal use.

**Architecture References**: Phase 3 (domain model, in full), Phase 4 §dependency direction (domain has zero infrastructure dependencies — this slice is the proof).

## Slice 2 — One contributor

- `IReviewContributor` contract (Phase 6 §2).
- One concrete contributor — Workflow Review itself (per the PRD and ADR-004), not a placeholder.
- `ContributorResult` (Phase 6 §4).
- A minimal orchestrator — enough to invoke one contributor and assemble its output into `Finding`s/`Recommendation`s, not the full DAG/composition machinery yet.
- Immutable review generation end to end, in memory.

**Architecture References**: Phase 6 §1–2 (lifecycle, contract), Phase 4 §inbound ports (initiate a review), ADR-001/ADR-002 (verify the orchestrator never touches `CanPublishWorkflow`).

## Slice 3 — Persistence

- Operational repository (Phase 5 §2, the lightweight queryable store).
- Evidence store (Phase 5 §2, the immutable evidence store — separate access pattern, per the principle, even if colocated initially).
- Snapshot manifest written once, per review, never recomputed (Phase 5 §3).
- Provenance wired through so every `Finding`/`Recommendation` is traceable (Phase 3 invariant 9, Phase 5 §7).
- Event publication — this is the point to finally resolve the open question carried since Phase 1: does this reuse the existing Audit Logger/Outbox Publisher, or is it a dedicated mechanism? Decide here, not before, now that the domain/application/integration event split (Phase 4) is implemented and testable.

**Architecture References**: Phase 5 (in full), Phase 4 §event classification, ADR-003 (evidence as primary artifact — this is where that stops being a documented intent and becomes an actual durable record).

## Slice 4 — Read models

- Review summary projection.
- Findings projection.
- Timeline projection.

Derived from published (immutable) reviews only — per Phase 5 §6, these should not need invalidation logic against a `Published` review, since it never changes after publication. This is the first slice that gives Studio (or any presentation layer) something to render.

**Architecture References**: Phase 5 §6 (read model separation), Phase 4 §presentation-communicates-only-with-application (verify no read model bypasses the application layer to read the aggregate directly).

## Slice 5 — Policy evaluation

- Policy evaluation port (Phase 4, outbound ports) — implemented for real, resolving PRD Open Question 2 (which policy-engine-shaped system, if any, supplies engineering-convention rules).
- Governance rules, freshness evaluation.
- `Verdict` generation (Phase 3 §Verdict, invariants 11–12 — no verdict before `EvaluationCompleted`, no `Published` without one).

This is the slice where the review stops being purely structural (did contributors run, were findings recorded) and starts reflecting actual engineering judgment against a real ruleset — the point the PRD's Purpose is really aiming at.

**Architecture References**: Phase 3 §Verdict + invariants 11–12, Phase 4 §policy evaluation port, Phase 2 (bounded context — confirm the ruleset is consumed, not owned, per the explicit non-ownership list).

## Slice 6 — Extension ecosystem

- Contributor registry (Phase 6 §1–2).
- Dependency DAG computation + cycle rejection at registration (Phase 6 §3).
- Registration validation.
- Failure isolation (Phase 6 §4) — exercised for real, with more than one contributor, for the first time.
- Multiple contributors running and composing (Phase 6 §5).

Only at this slice does the plugin architecture actually matter — deliberately last, since building it earlier would mean designing against a contributor ecosystem that doesn't exist yet.

**Architecture References**: Phase 6 (in full), ADR-005 (the append-only contributor model this slice finally exercises with more than one contributor).

## What this roadmap deliberately does not answer

- Timeframes/estimates for each slice — a project-planning decision, not an architectural one.
- Whether all six slices ship as M26.1 or whether later slices (5–6 in particular) become part of a subsequent milestone — a scoping decision for you to make, not implied by this roadmap's ordering.
- Team/ownership assignment per slice.
