# M26.1 — Architecture Phase 3: Domain Model

**Status:** Draft. Builds on Phase 2 (`M26.1-ARCHITECTURE-02-BOUNDED-CONTEXT.md`). Defines aggregates, entities, value objects, lifecycle, and invariants. Still not interfaces, ports, adapters, or events — that's Phase 4.

## Layering, per the application/domain split established in Phase 2

- **Application layer**: coordinates the use case — invoked at `publishVersion()` (per ADR-004), loads the three read-only inputs (new version's graph, prior version, capability registry) through the anti-corruption boundaries named in Phase 2, invokes the domain, persists the result, publishes events (mechanism TBD, per Phase 1/2's open note on Audit Logger/Outbox reuse).
- **Domain layer**: evaluates evidence, applies invariants, produces Findings and Recommendations. Never touches infrastructure, transport, or persistence directly — this is what keeps the evaluation engine reusable across future entry points (on-demand review, batch review, a hypothetical release-review contributor) without duplicating logic, per the earlier discussion of that benefit.

Everything below is domain layer unless noted otherwise.

## Aggregate roots

### `EngineeringReview` — the sole aggregate root

Owns:
- Its own lifecycle/state (below).
- A collection of `EvidenceReference` value objects (not full source data — see the Phase 2 refinement).
- A collection of `Finding` entities.
- A collection of `Recommendation` entities.
- A **`Manifest`** — a value object recording what this specific review actually covered: which workflow version, which prior version (if any), which capability-registry snapshot, which `EvaluationMetadata` — the reproducibility record for the review as a whole, distinct from any individual `EvidenceReference`.
- A **`Verdict`** — the aggregate's own overall conclusion (the domain-level counterpart to the PRD's clear/flagged/needs-attention recommendation), derived from the `Recommendation`s but held as a first-class member of the aggregate rather than something a caller has to recompute from the collection each time.

Only valid, named transitions are exposed — conceptually `beginEvaluation()`, `completeEvaluation()`, `publish()` — with invalid transitions refused internally rather than left to caller discipline (restating the Phase 3 lifecycle point at the behavior level, not just the state level).

Deliberately **not** modeled as separate aggregates: `Finding` and `Recommendation` are entities/immutable collections owned by `EngineeringReview`, not independent aggregates with their own identity and lifecycle. Reasoning: a `Finding` has no meaningful existence outside the review that produced it, and allowing independent modification of a `Finding` after the fact (the kind of thing a separate aggregate with its own repository would permit) would violate the append-only/immutability invariants below. Splitting these into their own aggregates would be modeling for a flexibility this domain explicitly doesn't want.

### `Finding` — entity, owned by `EngineeringReview`

- Append-only once added to a review — never edited or removed after creation.
- Always references at least one `EvidenceReference`; a `Finding` with no evidence reference is not constructible (see Invariants).
- Carries a `Severity` and a `Confidence` (value objects, below).

### `Recommendation` — entity, owned by `EngineeringReview`

- Derived from one or more `Finding`s; always references the findings that produced it.
- Immutable once generated.
- Never exists without at least one supporting `Finding` (see Invariants) — there is no path to construct a `Recommendation` independent of findings, which is what "recommendations never invent facts" means concretely at the model level.

## Value objects

- **`ReviewId`** — identity for an `EngineeringReview`.
- **`EvidenceReference`** — a citation into source data owned elsewhere: what was read (e.g., a specific node/edge in the workflow graph, a specific capability-registry entry, the prior version's corresponding element), not a copy of that data. This is the concrete mechanism behind the Phase 2 refinement — evidence-as-owned-by-this-context means owning the reference, not the referent.
- **`CapabilityReference`** — a citation into the capability registry specifically; a specialization of the evidence-reference pattern for that one source.
- **`PolicyEvaluation`** — the outcome of consulting an engineering-convention ruleset, if one exists (PRD Open Question 2 / Phase 2's note that this context consumes such a ruleset without owning it). Modeled as a value object now so the domain model isn't blocked on that open question being resolved — if no such ruleset exists at implementation time, this value object is simply unused rather than requiring a model change.
- **`Severity`** — attached to a `Finding`.
- **`Confidence`** — attached to a `Finding`; distinct from `Severity` (how bad, vs. how sure).
- **`ReviewSummary`** — the presentation object named in Phase 1/2; a value object derived from the aggregate's current Findings/Recommendations, not a separate source of truth.
- **`RecommendationPriority`** — attached to a `Recommendation`.
- **`EvaluationMetadata`** — when the evaluation ran, against which version, under which capability-registry snapshot — the contextual facts needed to make a review reproducible/explainable after the fact.
- **`Provenance`** — ties an `EvidenceReference` back to its exact source and moment of retrieval; the concrete mechanism behind the Explainability success metric (ADR-003) — every `Finding`/`Recommendation` should be traceable through `Provenance` back to a specific `EvidenceReference`.
- **`Timestamp`**.
- **`ReviewVersion`** — distinguishes this from `WorkflowVersion`: this identifies which version of the *review* (not the workflow) is being referenced, relevant since a workflow could plausibly be reviewed more than once against the same or different workflow versions.

## Lifecycle

```
Draft
  │
  ▼
EvidenceCollected
  │
  ▼
EvaluationCompleted
  │
  ▼
RecommendationsGenerated
  │
  ▼
Published
```

Each stage is a mandatory gate — no transition may skip a stage (e.g., `Draft` → `Published` directly is not a valid transition). This is enforced by the aggregate itself, not by calling-convention discipline in the application layer: `EngineeringReview` should refuse an out-of-order transition regardless of what the application layer attempts, since a state machine that can be violated by a careless caller isn't actually enforcing the invariant.

`Published` is terminal and immutable — once a review reaches `Published`, no further `Finding`s, `Recommendation`s, or state changes may be added to it (see Invariants). A workflow published again later produces a *new* `EngineeringReview` (new `ReviewId`, referencing the new `ReviewVersion`), not a mutation of a prior one.

## Core invariants (enforced by the domain model itself)

1. A review cannot reach `EvaluationCompleted` without at least one `EvidenceReference` recorded — no evaluation without evidence.
2. Every `Finding` references at least one `EvidenceReference`. Unreferenced findings cannot be constructed.
3. Every `Recommendation` references at least one `Finding`. Unreferenced recommendations cannot be constructed.
4. Once `Published`, the aggregate is immutable — no further mutation of any kind.
5. `EvidenceReference`s are append-only within a review — once added, never removed or altered.
6. `Finding`s never overwrite or invalidate previously recorded `EvidenceReference`s.
7. `Recommendation`s cannot introduce claims not traceable to their referenced `Finding`s ("never invent facts") — this is a modeling constraint on how `Recommendation` can be constructed, not just a documentation convention.
8. `PolicyEvaluation` (if used) is a delegated outcome the domain records, not something this domain computes itself — consistent with Phase 2's "consumes, does not own" stance on any convention ruleset.
9. Every `Finding` and `Recommendation` must be traceable to `Provenance` — the enforcement mechanism behind the Explainability success metric, not just an aspiration for it.
10. Authorization and structural validation remain untouched by any of the above — none of these invariants can produce a side effect on `CanPublishWorkflow` or `WorkflowValidator`'s outcomes (restating ADR-001/ADR-002 at the domain-model level, so it isn't only an integration-level promise).
11. A `Verdict` cannot exist before `EvaluationCompleted` is reached — no conclusion before the evaluation it concludes.
12. A `Published` review cannot exist without a `Verdict` — publication without a conclusion is not a valid end state.

## Relationships

```
EngineeringReview (aggregate root)
    ├── EvidenceReference[]   (citations into external, immutable source data —
    │                          not copies of Workflow-context or Capability-Registry
    │                          data; see Phase 2 refinement)
    ├── Finding[]             (entities, append-only, each referencing ≥1 EvidenceReference)
    ├── Recommendation[]      (entities, immutable once generated, each referencing ≥1 Finding)
    ├── Manifest              (what this review covered: versions, snapshot, metadata)
    ├── Verdict                (overall conclusion; cannot exist before EvaluationCompleted,
    │                           required for Published — invariants 11–12)
    └── ReviewState           (Draft → EvidenceCollected → EvaluationCompleted →
                                RecommendationsGenerated → Published)
```

`Evidence` itself — the source data an `EvidenceReference` points to — is not part of this aggregate and not owned by this bounded context; it lives in the Workflow-publication context (the graph) and the capability-registry context. This keeps the bounded-context boundary from Phase 2 intact at the domain-model level rather than letting implementation convenience quietly pull external aggregates' data into this one.

## What Phase 3 deliberately does not answer

- Repositories, ports, and how `EngineeringReview` is persisted/loaded — Phase 4 (Service Boundaries) and Phase 5 (Persistence Model).
- What domain events this aggregate emits (e.g., on reaching `Published`) and how they're published — Phase 4, informed by the still-open Audit Logger/Outbox question from Phase 1/2.
- The concrete shape of the `EngineeringReview` domain service(s) that implement the actual comparison/evaluation logic (workflow-diffing, capability-duplication detection, convention-rule consultation) — named as a responsibility in Phase 2, but its internal algorithm is out of scope for a domain *model* document and belongs in implementation design.
- Whether/how a second contributor (per ADR-005) would reuse any of these value objects versus defining its own — deferred until a second contributor is actually being designed, consistent with not building speculative generality now.
