# ADR-043: Adopt `packages/events` as the Execution event-delivery foundation

**Status:** Proposed (Phase 9e of `09-EXECUTION-LIFECYCLE-RUNTIME.md`; builds on `ADR-039`'s aggregate, `ADR-040`'s transition graph/canonical events, `ADR-041`'s orchestrator, `ADR-042`'s persistence)

## Context

9e's original proposed scope was built on a stated premise — "today: `OutboxRelay` → `InMemoryHiveEventBus` → Consumers" — that direct code inspection showed did not match the live system. Before building anything further on an inaccurate premise, the actual event-transport landscape was investigated in full (partly via a delegated read-only search). Six separate, real candidate systems were found:

1. **`packages/domain`'s own `EventBus`/`InMemoryEventBus`/`OutboxPublisher`** — real, and reachable: `AgentApplicationService`'s `CreateAgentCommand` path in `apps/platform-api/src/server.ts` actually constructs and calls it (correcting an earlier Slice 5 review finding of "unreachable").
2. **`packages/domain-model`'s `HiveEventBus`/`HiveDomainEvent`** (Slice 3) — confirmed zero consumers, unchanged from the earlier finding.
3. **`packages/core-bus`'s `DomainEventBus`/`CommandBus`/`QueryBus`** — real, constructed live in `server.ts`, but orphaned: nothing ever calls `.publish()` or `.register()` on it.
4. **`packages/events`' `NatsIntegrationEventPublisher`/`PollingRelayStrategy`/`OutboxRelayWorker`** — genuinely real NATS/JetStream publishing and outbox-table-polling code, but never instantiated or started anywhere, and not even exported from the package's own `index.ts` before this phase's repair.
5. **`packages/events`' own separate `PlatformEventBus`** (a second, independent mitt-based pub/sub inside the same package) and **`BaseWorker`** (whose `start()` is a literal `console.log` scaffold, extended by unreached `NotificationWorker`/`AiWorker` classes) — both scaffold-adjacent, not real transport.
6. **`apps/studio/platform`'s client-side kernel/events simulator** — a pre-existing, unrelated finding from the earlier Slice 5 review.

Given this landscape, whether to build a seventh, standalone event mechanism for `Execution` or adopt one of the existing real ones was raised explicitly. Per direction: **adopt `packages/events` as the foundation, conditional on its real components being genuinely salvageable** — repair them first if unwired/dependency-broken, and only build standalone if the package turned out to be fundamentally incompatible or costlier to fix than replace. Direct reading of `packages/events/src/{NatsPublisher.ts, RelayStrategy.ts, PollingRelayStrategy.ts, EventEnvelope.ts, OutboxRelayWorker.ts}` confirmed the trio is real, self-consistent code with only two defects: the package's own `index.ts` didn't export them, and `package.json` was missing the dependencies (`nats`, `@cerebro/core-bus`, `@cerebro/database`) and dev toolchain (`typescript`, `vitest`, `@types/node`) those files actually need — both cheap, mechanical repairs, not a redesign.

## Decision

**1. `packages/events` is adopted as the platform's real event-transport foundation for `Execution`'s canonical events, over `packages/core-bus`'s orphaned `DomainEventBus` and `packages/domain-model`'s unimplemented `HiveEventBus`.** Its `NatsIntegrationEventPublisher` (real NATS/JetStream publish), `PollingRelayStrategy` + `OutboxRelayWorker` (real outbox-table-polling relay), and `EventEnvelope` were repaired, not rewritten: `package.json` gained the missing dependencies and a `test` script; `index.ts` now exports them, with an explicit doc comment naming `./workers/BaseWorker` and its `NotificationWorker`/`AiWorker` subclasses as deliberately **not** part of this adoption (scaffold, flagged not fixed).

**2. `packages/domain` does not import `@cerebro/core-bus` or `@cerebro/events` directly.** `ExecutionOutboxEventPublisher.ts` defines `ExecutionIntegrationEventLike`/`ExecutionEventContext`/`ExecutionOutboxEventPublisher` — an interface deliberately shaped to be structurally identical to `packages/core-bus`'s real `IIntegrationEventPublisher` (`publish(event, context)`, `IntegrationEvent.type: string`, `RequestContext.tenantId: string`), confirmed by direct comparison of the real source files. A real `NatsIntegrationEventPublisher` instance satisfies this interface by TypeScript structural typing alone — no adapter class or cast needed. Same bounded-context-separation reasoning already applied to `ExecutionId` (off `packages/domain-model`'s `Identifier<Brand>`, `ADR-039` decision 5) and `ExecutionProviderPort` (off `HiveProviderExecutor`, `ADR-041`). It is also an honest environment constraint: `@cerebro/database` (a transitive dependency of both `@cerebro/core-bus` and `packages/events`) depends on a `@prisma/client` that has no generated client in this sandbox, so a real cross-package `tsc` build spanning both packages was not possible to run here — the structural-compatibility claim is verified by direct source comparison, not a live cross-package compile.

**3. `OutboxRelayExecutionEventSink` implements the `ExecutionEventSink` seam `ExecutionOrchestrator` (`ADR-041`) already accepted with zero changes.** It converts an `Execution` canonical `DomainEvent` into the `{ type, aggregateId, aggregateType, eventId, occurredAt, payload }` shape `ExecutionOutboxEventPublisher` (and transitively a real `NatsIntegrationEventPublisher`) expects, and delegates — it does not itself publish to NATS, write to any outbox table, or start any relay.

**4. Wiring a real `NatsIntegrationEventPublisher` (or the outbox-writing front half) into a live, running process remains unstarted.** No live NATS broker exists in this environment to verify against, and starting one would be live wiring — out of this phase's scope, same standalone discipline 9a–9d already used.

## Consequences

- `Execution`'s events now have a real, previously-broken-but-repaired delivery path available to adopt, rather than a sixth new mechanism invented from scratch — `packages/events`' NATS/outbox-relay code, dormant and unreachable before this phase, is now both exported and dependency-correct.
- `packages/core-bus`'s `DomainEventBus` and `packages/domain-model`'s `HiveEventBus` remain exactly as orphaned/unimplemented as this investigation found them — this ADR does not fix, deprecate, or remove either; that is separate, undecided future work.
- `BaseWorker`/`NotificationWorker`/`AiWorker`/`PlatformEventBus` remain scaffold, explicitly not touched or adopted by this phase.
- No live wiring: no process in this repository actually constructs an `OutboxRelayExecutionEventSink` backed by a real `NatsIntegrationEventPublisher` today. That remains a distinct, future integration milestone (candidate: the previously-proposed Phase 9g), same as 9c's orchestrator and 9d's repository remain unwired into `apps/platform-api`.
- The corrected finding that `OutboxPublisher` (not "OutboxRelay") is actually reachable via `CreateAgentCommand` supersedes the earlier Slice 5 review's "unreachable" verdict for that one specific path — noted here for the record, not re-litigated.

## Implementation status — Complete for 9e's own (standalone) scope; no live NATS broker touched

New files: `ExecutionOutboxEventPublisher.ts` (the structurally-compatible publisher contract), `OutboxRelayExecutionEventSink.ts` (the real `ExecutionEventSink` implementation). Repaired, not rewritten: `packages/events/package.json` (added `nats`, `@cerebro/core-bus`, `@cerebro/database` dependencies, `typescript`/`vitest`/`@types/node` devDependencies, a `test` script), `packages/events/src/index.ts` (now exports `EventEnvelope`, `RelayStrategy`, `PollingRelayStrategy`, `OutboxRelayWorker`, `NatsPublisher` — previously unexported real code — with an explicit doc comment on what is deliberately excluded). Both new domain-side files exported from `packages/domain`'s root `index.ts`. Verified, not assumed:

- Real `tsc --strict` typecheck (scratch-toolchain pattern) — clean across the whole `execution/` package, including the two new files.
- Real `vitest` run — event-shape conversion tests (canonical-event-to-integration-event shape, `occurredAt` ISO derivation) and a full-orchestrator-run integration test (every transition through `ExecutionOrchestrator.run()` reaches a recording fake publisher, in the correct order: `ExecutionValidatedEvent` → `ExecutionQueuedEvent` → `ExecutionStartedEvent` → `ExecutionCompletedEvent`), using a local fake standing in for a real `NatsIntegrationEventPublisher` (same public method shape) because this sandbox cannot resolve `@cerebro/events`'s transitive `@prisma/client` dependency — this proves the conversion logic is correct, not that a real NATS broker receives anything. All 101 tests across the whole `execution/` package passing (post the separate mandatory-version-concurrency reconciliation this same session also completed — see `ADR-042`'s "Amendment (post-9d)" section), clean `tsc --strict`.
- `packages/events`' own repair (package.json/index.ts) was not separately re-verified via a cross-package build in this sandbox, for the `@prisma/client`-generation reason stated above and in `ExecutionOutboxEventPublisher.ts`'s own doc comment — this is an honest, disclosed limitation, not a claim of full verification.
- Scratch verification artifacts removed after each run.
- **Test-count note (added during the Phase 9 stabilization review):** this ADR's "101 tests" figure is the same total `ADR-042`'s Amendment reports, not 101-plus-something-new. That is not a bookkeeping error: `OutboxRelayExecutionEventSink.ts` and its 3-test suite were already built, pre-compaction, as part of the same work sweep that produced 9d's original code — they were already counted inside 9d's pre-amendment "97," then carried through the reconciliation pass (their local fake was one of the "three test suites" the Amendment lists as updated to the new version-based contract) into the post-amendment "101." This ADR's own job was documenting that already-built 9e code and its landscape investigation, not writing new tests — hence "0 net new" here, unlike every ADR from 9f-1 onward, which does report an explicit "N new" breakdown for tests actually written during that ADR's own work.
- Not yet done, and not claimed as done: any live NATS broker or outbox-table wiring; live process construction of `OutboxRelayExecutionEventSink`; a real cross-package `tsc` build spanning `packages/domain`/`packages/events`/`packages/core-bus`/`@cerebro/database`; deprecation or removal of `packages/core-bus`'s orphaned `DomainEventBus` or `packages/domain-model`'s unimplemented `HiveEventBus`; anything involving `BaseWorker`/`NotificationWorker`/`AiWorker`/`PlatformEventBus`.
