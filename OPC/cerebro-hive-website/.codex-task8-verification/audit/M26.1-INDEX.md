# M26.1 — Workflow Engineering Review: Document Index

**Status:** Architecture complete. This is the single entry point for M26.1 — read this first, then follow into whichever document is relevant, rather than reading the full set in sequence every time.

## Foundation

1. `M26.1-ENGINEERING-REVIEW-ASSISTANT-BRIEF.md` — the original product brief, with explicit provenance labeling (grounded vs. proposed) and the M25 workflow-versioning verification that resolved the brief's one open factual assumption.
2. `M26.1-WORKFLOW-ENGINEERING-REVIEW-PRD.md` — product requirements: purpose, users, trigger, user journey, inputs, outputs, success metrics, non-goals. Product behavior only — no classes, APIs, or data models.
3. `adr/ADR-001` through `adr/ADR-005` — architectural invariants and the major decisions behind them (advisory-only review, `CanPublishWorkflow` as sole authorization authority, evidence as the primary artifact, integration with the workflow-publication lifecycle rather than CI/CD, and the append-only contributor extension model).

## Architecture specification

4. `M26.1-ARCHITECTURE-01-CONTEXT-DIAGRAM.md` — where Engineering Review sits relative to Workflow Studio, publication, policy evaluation, and reviewers; explicit in-scope/out-of-scope systems.
5. `M26.1-ARCHITECTURE-02-BOUNDED-CONTEXT.md` — domain responsibilities, ownership boundaries, what Engineering Review explicitly does not own, anti-corruption layers at the Workflow and Capability Registry boundaries.
6. `M26.1-ARCHITECTURE-03-DOMAIN-MODEL.md` — the `EngineeringReview` aggregate (with `Finding`, `Recommendation`, `Manifest`, `Verdict`), value objects, lifecycle, and twelve enforced invariants.
7. `M26.1-ARCHITECTURE-04-SERVICE-BOUNDARIES.md` — one-way dependency direction, inbound/outbound ports, and the domain/application/integration event classification.
8. `M26.1-ARCHITECTURE-05-PERSISTENCE-MODEL.md` — persistence principles (aggregates not object graphs, operational vs. immutable evidence stores, lineage-based versioning, repository scoping, read-model separation, evidence-reference identity vs. storage location, standardized ID types).
9. `M26.1-ARCHITECTURE-06-EXTENSION-FRAMEWORK.md` — the contributor "constitution": lifecycle, contract, dependency-DAG ordering, failure isolation, composition model, extension boundaries, and the determinism principle.

## Implementation

10. `M26.1-IMPLEMENTATION-ROADMAP.md` — six vertical slices (skeleton → one contributor → persistence → read models → policy evaluation → extension ecosystem), each tagged with the architecture sections it must conform to, and the traceability convention every implementation PR is expected to follow.
11. `M26.1-BASELINE.md` — the frozen baseline: implemented invariants and public extension points as built (Slices 1–2, `packages/engineering-review`), and the outstanding operational-verification checklist (`pnpm install`/`lint`/`typecheck`/`test`/`--coverage`) that has not yet run in any available environment. Treat this as the contract future slices and any M26.2/M26.3 work build on top of.

## How these documents relate

Each layer protects the one before it: the PRD defines intent, the ADRs establish invariants, the bounded context establishes ownership, the domain model encodes that ownership into enforceable constructs, service boundaries prevent infrastructure from violating it, the persistence model prevents storage from violating it, and the extension framework prevents future contributors from violating it. Determinism (Phase 6) is a derived consequence of the persistence model's manifest-as-snapshot principle (Phase 5), not an independently asserted rule — an example of how later documents build on earlier ones rather than restating them.

No further architecture documents are planned. The next work is implementation, starting with Slice 1 of the roadmap.
