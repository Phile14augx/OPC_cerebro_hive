# IMP-0003: Per-Agent Tool Authorization in HiveShield / tool-gateway

```yaml
id: "IMP-0003"
title: "Per-Agent Tool Authorization — HiveShield Policy Enforcement in tool-gateway"
source_knowledge:
  - "KN-SEC-000001"    # Prompt Injection Defense — privilege minimization requirement
  - "KN-INFRA-000001"  # MCP — all MCP invocations must route through HiveShield
  - "KN-AGENT-000002"  # Event-Driven Agents — event-triggered tool calls must be authorized

problem: >
  services/tool-gateway currently lacks per-agent tool authorization. Any registered agent
  can invoke any registered tool without per-agent policy enforcement. This violates the
  principle of least privilege: a data-retrieval agent should not have access to
  email-send or file-delete tools; an event-driven agent should not be able to invoke
  tools that require explicit human authorization just because an external event fired.
  
  The existing HiveShield policy package exists (packages/hiveshield-policy) but
  its tool authorization enforcement in tool-gateway is unconfirmed in the repository.
  
  IMP-0001 (Agent Subscription Registry) identified IMP-0003 as a security dependency:
  event-triggered agent paths must pass through HiveShield authorization before any tool
  invocation — no bypass for autonomous event-driven execution.
  
  KN-SEC-000001 (Prompt Injection Defense) identified privilege minimization as a P0
  defense: successful injection cannot cause harm if the agent lacks the tools to act.

proposed_solution: >
  Implement per-agent tool authorization in services/tool-gateway backed by
  packages/hiveshield-policy. Each registered agent has an explicit tool allow-list
  (the set of tools it is permitted to invoke). Tool invocations not on the allow-list
  are rejected with HTTP 403 before execution. The allow-list is managed via
  services/governance-api and requires tenant admin approval to modify.
  
  Authorization layers:
  1. Per-agent tool allow-list: (agent_id, tool_id) tuples with enabled/disabled state
  2. Per-tool risk classification: LOW (automatic) / MEDIUM (log + alert) / HIGH (human approval)
  3. Context gate: HIGH risk tools invoked from event-triggered paths require human approval
  4. Audit trail: every authorization decision logged to governance-api (required by P0 audit policy)
  
  This implements the minimum viable authorization model for safe agent operation.
  Future expansion: attribute-based access control (ABAC) for fine-grained parameter restrictions.

business_value: >
  Enables safe production deployment of agents. Enterprise customers require documented
  authorization controls as a precondition for procurement. Without per-agent authorization,
  Cerebro cannot make security claims about its agent products. Directly required by:
  - IMP-0001 (Agent Subscription Registry): security dependency
  - IMP-0002 (MCP Server): all MCP invocations must be authorized

technical_value: >
  Implements the principle of least privilege at the tool invocation layer.
  Reduces blast radius of prompt injection attacks (KN-SEC-000001):
  even if an agent is hijacked, it can only invoke tools on its allow-list.
  Provides the authorization enforcement point for all agent tool calls —
  MCP, direct API, webhook-triggered — in a single enforcement layer.

affected_components:
  - "services/tool-gateway"
  - "packages/hiveshield-policy"
  - "services/governance-api"
  - "packages/agent-sdk"   # agent registration must include tool allow-list

dependencies:
  - "Existing tool registry in tool-gateway (tool_id, tool_name, schema)"
  - "Existing agent registry in swarm-runtime (agent_id, tenant_id)"
  - "packages/hiveshield-policy (policy engine — may need authorization query API)"
  - "services/governance-api (audit log, approval workflow)"

security_implications: >
  This IMP IS the security control. Implementation must:
  1. Enforce authorization synchronously before tool execution — no async gaps
  2. Fail closed: if policy lookup fails, DENY the tool invocation (do not allow)
  3. Deny by default: new agents have an EMPTY allow-list; tools must be explicitly granted
  4. Audit every decision: approved AND denied invocations logged to governance-api
  5. Tenant isolation: agent A cannot invoke tools granted to agent B even in same tenant
  6. Admin-only modification: allow-list changes require tenant admin role; RBAC enforced
  7. No bypass path: event-triggered agent tool calls go through the same enforcement
     as interactive agent calls — no "trusted event" shortcut

estimated_complexity: MEDIUM
priority: P0

acceptance_criteria:
  - "Agent with allow-list [tool_A, tool_B] cannot invoke tool_C — returns 403"
  - "New agent with empty allow-list cannot invoke any tool — all return 403"
  - "Tenant admin can grant tool to agent via governance-api PATCH /v1/agents/{id}/tools"
  - "All authorization decisions (allow AND deny) logged with: agent_id, tool_id, tenant_id, timestamp, decision, reason"
  - "HIGH-risk tool invocation from event-triggered agent returns 202 PENDING until human approval"
  - "Policy lookup failure results in DENY (fail-closed behavior)"
  - "Tool allow-list modification requires tenant admin JWT role claim"
  - "Authorization enforcement is synchronous: no tool execution begins before policy returns ALLOW"

tests_required:
  - "Unit: allow-listed tool invocation succeeds"
  - "Unit: non-allow-listed tool invocation returns 403"
  - "Unit: empty allow-list blocks all tool invocations"
  - "Unit: policy lookup failure → DENY (fail-closed)"
  - "Integration: event-triggered agent → tool invocation → HiveShield → allow → execute → audit log"
  - "Integration: event-triggered agent → HIGH risk tool → HiveShield → PENDING → human approval → execute"
  - "Security: cross-tenant tool access blocked (agent_id from tenant A cannot use tool granted to tenant B)"
  - "Security: allow-list modification without admin role rejected"
  - "Load: 1000 concurrent tool invocations, all authorized within 50ms p99"

status: BACKLOG
```
