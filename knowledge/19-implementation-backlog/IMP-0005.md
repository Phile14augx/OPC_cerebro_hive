## Problem Statement

`services/memory-service` currently implements only Tier 1 (in-context/working memory) — all memory exists exclusively in the agent's context window and is discarded when the session ends or the service restarts. This means:

- CerebroAgents have **no memory across sessions** — every firing starts from scratch
- **No episodic continuity** — an agent that processed a critical alert cannot recall it in the next firing
- **No semantic knowledge accumulation** — agent-learned facts about tenant data patterns are lost
- **In-process memory cannot scale** — cannot run multiple memory-service instances without memory divergence

The PROGRESS.md audit explicitly flags `InMemoryExecutionRepository` as a P0 risk. MemGPT (arXiv 2310.08560) provides a peer-reviewed, commercially deployed solution (Letta) that maps directly to the Cerebro stack: PostgreSQL + pgvector is already present.

## Solution Architecture

### Memory Tier Taxonomy (per CoALA + MemGPT)

```
Tier 1 — In-Context / Working Memory
  Storage: Agent context window (volatile)
  Scope: current session only
  Owner: packages/agent-sdk (unchanged)
  Persistence: NONE — lost on session end
  Capacity: model context window limit
  
Tier 2 — Episodic Memory  ← IMP-0005 Phase 1
  Storage: PostgreSQL + pgvector (AgentMemory table)
  Scope: per-agent, per-tenant, searchable by semantic similarity
  Owner: services/memory-service
  Persistence: TTL-based (default 90 days, tenant-configurable)
  Capacity: unlimited (database-bound)
  Access: semantic search + recency retrieval
  
Tier 3 — Semantic / Knowledge Memory  ← IMP-0005 Phase 2
  Storage: PostgreSQL + pgvector (AgentKnowledge table)
  Scope: per-agent, per-tenant, importance-scored
  Owner: services/memory-service
  Persistence: indefinite (no TTL; pruned by importance score)
  Capacity: configurable per tenant
  Access: vector similarity search with importance filter
  
Tier 4 — Procedural Memory (FUTURE)
  Storage: system prompts + tool definitions (static)
  Scope: per-agent-type, shared across instances
  Owner: packages/agent-sdk (system prompt templates)
  Persistence: configuration-managed
  Note: not modified at runtime; out of scope for IMP-0005
```

### Phase 1 — Episodic Memory (Week 1–2)

**Database schema** (Prisma — extends existing `schema.prisma`):

```prisma
model AgentMemory {
  id          String   @id @default(cuid())
  agent_id    String
  tenant_id   String
  session_id  String
  role        String   // 'agent' | 'user' | 'system' | 'tool'
  content     String   // text content of the memory
  summary     String?  // agent-generated summary (shorter than content)
  embedding   Unsupported("vector(1536)")  // pgvector; 1536 = text-embedding-3-small dims
  importance  Float    @default(0.5)       // 0.0–1.0; scored by agent at store time
  memory_type MemoryType
  created_at  DateTime @default(now())
  expires_at  DateTime?                    // null = no expiry; set by tenant retention policy
  
  @@index([agent_id, tenant_id])
  @@index([tenant_id, created_at])
}

enum MemoryType {
  EPISODIC    // a specific event/observation from a session
  SEMANTIC    // a general fact or learned pattern
  PROCEDURAL  // a skill or instruction (rarely written at runtime)
}
```

**Memory service API** (new endpoints on `services/memory-service`):

```typescript
// Store a memory after a firing completes
POST /v1/memory
{
  agent_id: string
  tenant_id: string
  session_id: string
  role: 'agent' | 'user' | 'tool'
  content: string          // what to remember
  memory_type: 'EPISODIC' | 'SEMANTIC'
  importance: number       // 0.0–1.0
  ttl_days?: number        // defaults to tenant.memory_retention_days (90)
}

// Retrieve relevant memories before a firing
GET /v1/memory/search
{
  agent_id: string
  tenant_id: string
  query: string            // semantic search query (embedded server-side)
  k: number               // top-k results (default: 5)
  min_importance?: number  // filter threshold (default: 0.3)
  max_age_days?: number    // recency filter (default: no limit)
  memory_type?: MemoryType
}

// Expire memories past TTL (cron job)
DELETE /v1/memory/expired
```

**Agent SDK integration** (new `AgentMemoryClient` in `packages/agent-sdk`):

```typescript
export class AgentMemoryClient {
  async recall(query: string, opts: RecallOptions = {}): Promise<MemoryResult[]> {
    const results = await this.memoryService.search({
      agent_id: this.agentId,
      tenant_id: this.tenantId,
      query,
      k: opts.k ?? 5,
      min_importance: opts.minImportance ?? 0.3,
      max_age_days: opts.maxAgeDays,
    })
    return results
  }
  
  async remember(content: string, opts: RememberOptions): Promise<void> {
    await this.memoryService.store({
      agent_id: this.agentId,
      tenant_id: this.tenantId,
      session_id: this.sessionId,
      role: opts.role ?? 'agent',
      content,
      memory_type: opts.memoryType ?? 'EPISODIC',
      importance: opts.importance ?? 0.5,
      ttl_days: opts.ttlDays ?? this.tenantConfig.memoryRetentionDays ?? 90,
    })
  }
  
  // Page-in pattern (MemGPT): prepend relevant memories to context
  async pageIn(currentContext: string): Promise<string> {
    const memories = await this.recall(currentContext, { k: 5, minImportance: 0.3 })
    if (memories.length === 0) return currentContext
    const memoryBlock = memories
      .map(m => `[Memory ${m.created_at}] ${m.summary ?? m.content}`)
      .join('\n')
    return `## Relevant Past Context\n${memoryBlock}\n\n## Current Context\n${currentContext}`
  }
}
```

**Standard agent firing pattern** (using new memory client):

```typescript
// At start of every agent firing:
const recentContext = await agent.memory.pageIn(currentEvent.summary)

// During firing — store important observations:
await agent.memory.remember(
  `Tenant ${tenantId} alert: ${alert.description} — resolved via ${resolution}`,
  { memory_type: 'SEMANTIC', importance: 0.8 }
)

// At end of firing — store episodic record:
await agent.memory.remember(
  firing.summary,
  { memory_type: 'EPISODIC', importance: firing.importanceScore }
)
```

### Phase 2 — Semantic Memory + Importance Scoring (Week 3)

**Importance scoring function** (determines what gets stored long-term):

```typescript
export function scoreImportance(event: AgentEvent): number {
  let score = 0.5  // baseline
  
  // Boost for high-severity events
  if (event.severity === 'CRITICAL') score += 0.3
  if (event.severity === 'HIGH') score += 0.2
  
  // Boost for novel information (not similar to recent memories)
  const similarity = await agent.memory.maxSimilarity(event.summary)
  if (similarity < 0.7) score += 0.15  // novel → worth remembering
  
  // Boost for user-confirmed important events
  if (event.userConfirmed) score += 0.25
  
  // Decay for routine/repetitive events
  if (event.isRecurring && event.recurrenceCount > 10) score -= 0.2
  
  return Math.max(0.0, Math.min(1.0, score))
}
```

**Memory pruning policy** (runs nightly via Temporal.io cron):

```typescript
// Pruning rules:
// 1. Delete EPISODIC memories past TTL (respects tenant retention days)
// 2. Compress EPISODIC memories with importance < 0.3 into SEMANTIC summary
// 3. Keep SEMANTIC memories indefinitely up to tenant quota
// 4. Alert tenant admin when approaching memory quota (80% full)
```

## Privacy and Security Requirements

1. **Tenant isolation** — All memory queries MUST include `WHERE tenant_id = $tenantId AND agent_id = $agentId`. No cross-tenant memory leakage is possible by design (not just by policy).

2. **Encryption at rest** — `content` and `summary` columns MUST be encrypted using PostgreSQL `pgcrypto` (AES-256). Encryption key per tenant, managed via `packages/secrets-core`.

3. **Right to deletion** — `DELETE /v1/memory?tenant_id={id}` wipes all memories for a tenant. Required for GDPR/data subject erasure requests. Must complete within 24 hours.

4. **Memory content never logged** — Memory content (the `content` field) MUST NOT appear in telemetry spans or application logs. Only `memory_id`, `agent_id`, `tenant_id`, `importance`, and `memory_type` are loggable.

5. **Embedding privacy** — Embeddings are generated server-side in `services/memory-service` using a local embedding model or OpenAI `text-embedding-3-small`. No raw content is sent to external embedding API without tenant consent flag.

## Acceptance Criteria

1. **Persistence** — Agent memories survive service restart. Verify: store 3 memories → restart memory-service → recall memories → all 3 returned.

2. **Semantic search** — A memory stored with content "PostgreSQL connection pool exhausted at 200 connections" is recalled by query "database connection issues". Cosine similarity ≥ 0.75.

3. **Tenant isolation** — Tenant A cannot retrieve Tenant B's memories regardless of query. Verify by direct API call with tenant A credentials querying agent from tenant B context.

4. **TTL expiry** — Memories with `expires_at` in the past are not returned by search and are deleted by the nightly prune job.

5. **Importance filter** — Memories with `importance < 0.3` are not returned when `min_importance = 0.3`. Verify with 10 low-importance memories in store.

6. **Encryption** — Direct database inspection of `agent_memory` table shows `content` column is ciphertext (not plaintext). Decryption requires the tenant's key.

7. **Deletion** — `DELETE /v1/memory?tenant_id=X` removes all memories for tenant X within 5 minutes. Verify with count check before and after.

8. **Performance** — Memory recall (semantic search, k=5, 10,000 stored memories) completes in ≤200ms p95. Verify with pgvector index (IVFFlat or HNSW).

9. **Memory content not in logs** — No telemetry span or application log contains the `content` field value from AgentMemory. Verify by log scan after 100 recall operations.

10. **pageIn integration** — An agent that fired previously and stored an EPISODIC memory has that memory prepended to its context window on the next firing (confirmed by context snapshot assertion in integration test).

## Migration Path

`services/memory-service` currently has an `InMemoryRepository` class. Migration:

1. Create `PostgresMemoryRepository` implementing the same interface as `InMemoryRepository`
2. Run both in parallel for 1 week (write to both, read from Postgres, fall back to in-memory)
3. After validation: remove `InMemoryRepository`; Postgres becomes sole repository
4. No data migration needed (in-memory data is ephemeral and has no historical value)
