technical_mechanism: >
  GraphRAG operates in two phases:
  
  INDEXING PHASE (offline, expensive):
  1. Text splitting: source documents → text chunks (configurable chunk size)
  2. Entity extraction: LLM extracts (entity_name, entity_type, description) tuples
     from each chunk. Runs LLM N times per document — expensive.
  3. Relationship extraction: LLM extracts (source_entity, target_entity, relationship_description,
     strength) tuples from chunks.
  4. Knowledge graph construction: entities as nodes; relationships as weighted edges.
  5. Community detection: Leiden algorithm clusters the graph into hierarchical communities
     at multiple resolution levels.
  6. Community summary generation: LLM generates a summary for each community (expensive —
     proportional to number of communities).
  7. Embedding: all summaries and entity descriptions are embedded into vector space.
  
  QUERY PHASE (online):
  Global queries: retrieve top-K relevant community summaries → map (generate partial answers
  per community) → reduce (synthesize final answer from partial answers). Uses MapReduce pattern.
  Local queries: vector similarity search on entity embeddings + neighborhood traversal in graph.
  Hybrid: router or user-specified mode.
  
  Cost profile: indexing is 10–100× more expensive than naive RAG indexing.
  Query time: comparable to naive RAG for local; higher for global (MapReduce LLM calls).

  Naive RAG retrieves isolated document chunks based on semantic similarity to the query.
  This fails for questions requiring global understanding of a dataset: "What are the
  main themes?", "What risks appear most frequently?", "How do these entities relate?"
  GraphRAG captures relationships and hierarchical structure that flat embedding search misses.
  Critical for enterprise knowledge bases where interconnected domain knowledge matters
  (regulatory documents, scientific literature, corporate policies).
